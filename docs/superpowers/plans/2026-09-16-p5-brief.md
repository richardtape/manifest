# P5 brief — contract and clients (Phase 1c)

*Written 2026-09-16, straight after P4c was executed, for the agent that writes P5. It compares
what §17, §22 and the roadmap ask of 1c with the code as it stands at `853fb17`, and records three
measurements taken that day (§2.3, §3). §5 lists the five decisions that were Rich's; **all five were decided on 2026-09-16 and applied to
the spec (`1d88846`)**, and ORIENTATION §7e turns them into the P5a task. Read it with the spec open — every
section number below is the spec's.*

---

## 1. The requirement

**§17, 1c:** OpenAPI generation, versioned TS client, `manifest-mock`, delegated tokens and
`PendingAction` (D24), the knowledge pack API (D25), `console/` with its import boundary, a
read-only `LaunchReadiness` view, **the audience question at project creation (§24) and a
read-only fleet list**, the CI acceptance script. **Demo:** the §1 journey, clickable, run twice
over one contract. **Question:** *Is the API complete, and can a second developer reproduce all
of it?*

**§22's journey** — the thing both clients must drive, and the definition of "done":

1. Log in with CWL (Manifest IdP, test user)
2. Create a project — name and blueprint
3. Watch provisioning: repository created, `manifest.yaml` validated
4. Trigger a build; build logs stream live
5. Deploy to staging; instance state transitions stream live
6. Open the running app; log in with CWL *inside* it; write a note; ask the LLM
7. Request production; see `LaunchReadiness` (§13) with its blocked items and why

**§1's success criterion** adds the bar that matters most: *driven by a human through a UI, not
by `curl`*, on a MacBook with no cloud dependencies.

**The roadmap's P5 section disagrees with §17 in one place:** it omits *a read-only fleet list*.
§17 is the spec and wins; the roadmap section has been corrected alongside this brief.

**Binding design constraints** (§22, D22–D25, §20): the console imports **only** the generated
client, enforced by a lint boundary **and** a test; no capability in the console that the API
lacks; resource-oriented, never view-oriented; one event stream per project; idempotency keys on
every mutation; machine-actionable errors; the contract generated from the routes, checked in,
drift failing the build, and `manifest-mock` validated against the same document; a delegated
token never carries production promotion, secret read, quota change or member management —
requesting one creates a `PendingAction` a human resolves interactively, **enforced centrally, not
per route**; per-token rate limits; CSRF on every state-changing route; the first administrator
created by a documented out-of-band procedure.

## 2. What exists today — read from the code on 2026-09-16

### 2.1 The API surface: 18 routes a client could use, and 2 that are internal

| Area | Routes | Notes |
|---|---|---|
| Auth (`api/routes/auth.ts`) | `GET /auth/login`, `POST /auth/saml/callback`, `GET /auth/me`, `POST /auth/logout` | The callback redirects to `/auth/me` — its own comment says *"P5 changes this line, not the flow"*. No return-to. |
| Projects (`api/routes/projects.ts`) | `POST /projects`, `GET /projects`, `GET /projects/:projectId` (`?expand=environments`), `GET` and `POST /projects/:projectId/spec`, `POST /projects/:projectId/members` | No blueprint listing, no member listing or removal. |
| Delivery (`api/routes/delivery.ts`) | `POST /projects/:projectId/builds`, `GET /builds/:buildId`, `GET /builds/:buildId/logs`, `POST /projects/:projectId/releases`, `POST /environments/:environmentId/deploy`, `GET /environments/:environmentId`, `GET /environments/:environmentId/incidents` | No list of a project's builds or releases; no `GET /releases/:id`. |
| Events (`api/routes/events.ts`) | `WS /projects/:projectId/events` | Cookie-authorized **before** the upgrade; replay of 50, a ready frame, then live; 1013 past 1 MB of backlog. Frames: `kind: event`, `log`, `control` (`observability/bus.ts`). |
| Internal (`api/routes/registry-token.ts`) | `POST` and `GET /internal/registry/token` | The registry's token realm. **Must stay out of the published contract.** |

**How a request becomes an actor** (`api/server.ts`): one `onRequest` hook reads the
`manifest_session` cookie — an HMAC-signed, stateless token, 12 h, `SameSite=Lax`, `HttpOnly`,
`Secure` only outside development (`identity/session.ts`). **There is no bearer credential of any
kind**, no `sessions` table (§20 says *server-side session store*, so logout cannot revoke a
session — a divergence to record, not necessarily to fix), and **no explicit CSRF control**: a
cross-site form POST is refused today only because the idempotency hook demands an
`Idempotency-Key` header a form cannot send, and the two routes exempt from it
(`/auth/logout`, `/auth/saml/callback`) are the ones a browser console will exercise first.

**How a route is defined:** Fastify with **no route schemas at all**. Bodies are parsed with zod
**inside** handlers; responses are **Drizzle rows returned as-is** — `POST .../releases` returns the
release row (with `resolvedConfig`), `POST .../deploy` the instance row (with `driver` and
`handle`). There is nothing yet to generate an OpenAPI document *from*, and the public shape of
every resource is currently "whatever the table has". **Designing the public representations is
P5's largest single piece of work, and it is invisible in §17's one-line list.**

**Errors** (`api/errors.ts`): `{ error: { code, message, hint } }`, with extra fields in places
(`launchReadiness` on the production 409). Codes are string literals spread across modules — there
is no registry a client can switch on.

**Idempotency** (`api/idempotency.ts`): every mutating route except `/auth/*` and the registry realm
requires `Idempotency-Key` (≥ 8 chars); same key and body replays, different body is `409`. The
generated client and `manifest-mock` must both honour it.

**The authorization contract suite** (`api/authz-contract.ts`, §16) exercises every registered
route as owner, collaborator, stranger, admin and anonymous, and **a completeness check fails when a
route is registered that the suite does not list** (`app.registeredRoutes`). Every route P5 adds
must be added there; delegated tokens add at least three actors to the matrix.

### 2.2 What the journey needs that is not there

- **Step 2–3, project creation seeds a stub, not an app.** `POST /projects` writes a four-line
  `manifest.yaml` (no `auth`, no `services`, no `ai`) and `src/index.js` containing one import line.
  **It does not copy the blueprint skeleton.** Every demo builds a working app by cloning the bare
  repository from disk and pushing `blueprints/node-ts-mongo/skeleton` with `fixtures/proof-app`
  laid over it (`scripts/lib/proof-app.sh`). A browser cannot push to a path on the laptop, so
  **a console-created project cannot reach step 6** — see §5, decision 1.
- **Step 3, "watch provisioning".** Creation is synchronous inside `POST /projects` and publishes
  no event: `observability/events.ts` has 12 event types and none is `project.created` or
  `spec.validated`.
- **Step 5, "instance state transitions stream live".** Only `instance.healthy`, `instance.failed`,
  `instance.retiring`, `instance.retired` and `instance.retire_failed` are published; nothing for
  `provisioning` or `starting`.
- **Steps 4–5 run inside the HTTP request.** A build returns when the image is pushed; a deploy
  returns once the new instance serves (Rich's **R3** in P4c) — ~5.4 s when healthy, **~91 s** when a
  release never becomes ready. A browser tab and a CI script will hold those requests open.
- **Step 7, `LaunchReadiness` is a constant.** A production deploy answers `409
  RELEASE_PRODUCTION_GATE_UNAVAILABLE` carrying a hard-coded five-item array in
  `api/routes/delivery.ts`, each item stamped `deliveredBy: 'P4'` or `'P3'` — **stale: none of
  `IamRegistration`, `PrivacyAssessment`, the rehearsal or `AdminApproval` exists, and they are
  Phase 2's (P6, P8)**. There is no readiness resource, and **scan results are not persisted
  anywhere** — `runtime/docker/driver.ts` prints unfixable findings to stderr and says *"Persisting
  these on the Release row is owed and is `releases/`'s to do"*, so the one item Manifest could
  compute today (§13's *dependency and secret scans clean*) has no data behind it.
- **Audience (§24, D29).** `projects.audience` exists as a nullable jsonb column; `POST /projects`
  does not accept it, and nothing records `set_by`/`set_at`.
- **Fleet list.** `GET /projects` already returns every project to an admin — but **no admin can
  exist**: `users.role` defaults to `member`, and there is no bootstrap procedure, script or RUNBOOK
  entry. §20 requires a documented out-of-band one.
- **Knowledge pack (D25).** `blueprints/node-ts-mongo/agents/AGENTS.md` exists; no route serves it,
  and no route lists blueprints (the console's step 2 needs one).
- **D24.** No `DelegatedToken`, no `PendingAction`, no bearer authentication, no per-token rate
  limit. `POST /projects/:projectId/members` — one of D24's privileged four — exists today with no
  step-up and would be reachable by a token the moment tokens exist.

### 2.3 Tooling, infrastructure and process

- **One workspace package**, `packages/control-plane`. No React, no Vite, no OpenAPI or client
  tooling. ESLint's rules target `packages/control-plane/src/**`; Vitest's workspace has two projects,
  both rooted in the control plane; Prettier owns `packages/`. `contract/`, `mock/` and `console/`
  (§5's module map) have nowhere to live yet, and `module-boundaries.test.ts` only sees the control
  plane.
- **zod 3.25.76, Fastify 5.12.3 — and zod 3.25 already ships `zod/v4`.** Measured 2026-09-16:
  `import('zod/v4')` exposes `z.toJSONSchema`, which turned a two-field object into a draft 2020-12
  schema (the dialect OpenAPI 3.1 uses) with `required` and `additionalProperties: false`, **with no
  new dependency**. The routes' existing schemas are written against zod 3's API, so using it means
  moving them to the `v4` import, not adding a library.
- **"CI" does not exist** — no workflow of any kind. §16's *drift fails CI* and 1c's *CI acceptance
  script* must be defined as local gates and `make` targets.
- **The control plane is not behind the edge.** It listens on `127.0.0.1:7100`; its own SP's ACS is
  derived from `MANIFEST_CONTROL_PLANE_ORIGIN` (default `http://127.0.0.1:7100`) and re-registered at
  boot (`sso/platform.ts`). The edge's Caddyfile serves `idp.manifest.internal` and a wildcard
  placeholder for `*.manifest.internal` — `console.manifest.internal` currently answers
  `manifest OK …`. Ports **7101** (admin UI), **7102** (`manifest-mock`) and **7104** (console) are
  reserved and unused.
- **Every demo script and RUNBOOK section speaks `http://127.0.0.1:7100` with `curl`.** Any change to
  the API's origin or paths moves all four demos, `scripts/lib/proof-app.sh`, `idp-login.sh`,
  README's *Running the control plane*, RUNBOOK and WALKTHROUGH.
- **Adding dependencies needs the network**, and pnpm 11 refuses install scripts not named in
  `allowBuilds`. The control plane's own dependency tree is **not scanned** by anything (P4a) — a
  console and a client generator enlarge it.

### 2.4 Found while applying the decisions — both are P5a's to handle

- **Nothing reserves a slug, so a project could claim a platform hostname.** Slugs are
  `^[a-z][a-z0-9-]{2,38}$` with no exclusions, and a production app lives at
  `<slug>.manifest.internal` (§23) — the same shape as `idp.manifest.internal`, which the Manifest
  IdP already uses, and `console.manifest.internal`, which the console will. A project named `idp`
  or `console` would claim the platform's own name the day production deploys exist. **§23 now
  reserves four groups of labels** — Manifest's own surfaces, sign-in and identity words,
  environment and infrastructure words, and names software resolves unasked — **and specifies
  `GET /v1/slugs/{slug}`**, which answers exactly what project creation will. P5a builds both: one
  validation function behind the check, creation and renames (`SLUG_INVALID`, `SLUG_RESERVED`,
  `SLUG_TAKEN`), the list as configuration in one place, the test §23 asks for (the edge serves no
  platform name the list lacks), and the check's row in the authorization contract suite.
- **The list already exists as data — P5a loads it, it does not write it.** Rich added two UBC
  groups the same day (spec commit `5065c13`), and the whole list is `infra/reserved-labels/`:
  `labels.yaml`, hand-maintained (Manifest's own names, sign-in words, environment words, names
  software resolves unasked, and UBC's campuses, shared services and everyday unit names), and
  `ubc-academic.yaml`, **generated** from UBC's Vancouver and Okanagan academic calendars by
  `generate-ubc-academic.mjs` — every faculty, school, department and course subject, by name and
  abbreviation. **755 labels**, each with the sentence the slug check returns; all satisfy §7's slug
  rule and none is in two groups (checked 2026-09-16 with the control plane's own `yaml` package).
  **None of the 59 slug-shaped names the repository's tests, demos and fixtures use is reserved**, so
  enforcing the list breaks no existing test — but a new test fixture named after a subject (`chem`,
  `math`, `law`) will be refused, which is the rule working.
- **The slug rule is written four times today**, and a fifth copy would be the check's: the regex
  `^[a-z][a-z0-9-]{2,38}$` is in `spec/schema.ts` (`SLUG`), `projects/repository.ts`,
  `source/local-driver.ts` and the zod body in `api/routes/projects.ts` (read 2026-09-16), with the
  hint text in `spec/errors.ts`. §23's *one function answers both* means collapsing them into the one
  function, not adding the reserved list as a sixth place a name is judged.
- **`make verify` uses `console.manifest.internal` as its probe of the edge.** Read 2026-09-16:
  three DNS checks resolve that name (`scripts/verify.sh` 28, 37, 53 — they keep passing), and four
  checks fetch it through the edge — *a container reaches https://console…* (106) and *the host reaches
  https://console…* (744), which both require the placeholder body `host=console…`, the keychain
  certificate check (752), and the host/container **parity** assertion after it, which compares the two
  bodies. `scripts/doctor.sh` line 267 fetches it too. **The task that serves the console there turns at
  least the two placeholder checks red, and the parity check red as well if the edge answers the
  container differently** — move those probes to a name that is guaranteed never to be routed in that
  same task, and say so in ORIENTATION §4.

## 3. Measured on 2026-09-16

**The edge can front the control plane, over trusted TLS, from the host and from a container.** A
throwaway route `p5-probe.manifest.internal` → `host.docker.internal:7100`, added through the admin
API with the control plane running:

| Probe | Result |
|---|---|
| host → edge → control plane, `GET /auth/me` | `401` envelope, **22 ms** |
| `GET /auth/login` through the edge | `302` to `https://idp.manifest.internal/…` — a login would still come back to `127.0.0.1:7100`: the AuthnRequest's callback is `config.entity.acsUrl` (`identity/saml.ts`), derived from `MANIFEST_CONTROL_PLANE_ORIGIN`, which did not change (read from the code, not decoded from the request) |
| WebSocket upgrade, anonymous, through the edge | `401` from the route's pre-upgrade hook — the upgrade reaches the route |
| a container on `manifest-platform` → edge → control plane | `401` envelope |

The route was deleted and the hostname went back to the placeholder; the control plane was
stopped. **What this does not show:** a full login through the edge (the origin and SP registration
must move first), a browser, or an upgrade that completes.

**The consequence to take seriously — measured from inside the running proof app's container.** S6
probe 2 proves an app container cannot reach the control plane **on the host**. But every app network
has `manifest-caddy` on it, and **the edge answers any platform hostname asked of it by address**:
inside the app, `getent hosts console.manifest.internal` fails (exit 2) — the name does not resolve
— yet an HTTPS request to the edge's address on that network (`172.30.0.2`) with
`console.manifest.internal` as SNI and `Host` came back **`200 manifest OK
host=console.manifest.internal … remote=172.30.0.7`**. Name resolution is not a boundary. So **any
route P5 puts on the edge for the API is reachable from every app container**, and in Phase 3 from
every sandbox, which §16's security tier says must not reach the control plane. Nothing tests that
path today because nothing routes it. The same measurement shows the way to close it: the edge sees
the caller's **app-network address** (`remote=172.30.0.7`), so a route can refuse app networks by
source, and an S6 probe can prove it with a positive control from the host.

> **ALL FIVE ARE DECIDED — RICH, 2026-09-16 — AND THE SPEC CARRIES THEM (commit `1d88846`). Do not
> re-open any of them.**
> **1 — (a), starters.** **2 — three plans, P5a, P5b, P5c**, each written after the one before it
> executes. **3 — (a): the console and the API on one origin, `console.manifest.internal`, through
> the edge, with the edge refusing the control plane's routes to app and sandbox networks.**
> **4 — a `/v1` path prefix.** **5 — P5's acceptance does NOT depend on a clean machine or a second
> developer**; §17's 1c question now says so, and the second-machine clone stays in RUNBOOK's *Known
> gaps*.
> Applying decision 3 safely needed one more rule, applied with it: **§23 reserves labels as project
> slugs** — see §2.4. **Rich then extended it the same day** (spec commit `ecf5f29`): four groups of
> reserved labels, each with its reason, and **a slug check API — `GET /v1/slugs/{slug}` — so a client
> can tell a person whether a name will work while they type it.**

**1. What a project created from the console contains.** §22 says step 2 is *"choose a blueprint"*
and step 6 is *sign in, write a note, ask the LLM* — but a blueprint skeleton has no notes and no
question, and today's creation does not even copy the skeleton. Options:
(a) **seed the skeleton, and give the blueprint catalogue *starters*** — `node-ts-mongo@1` ships the
proof app as a starter the person chooses at creation; §25's descriptor gains `starters:` and §22's
step 2 becomes *choose a blueprint and a starter*. The skeleton stays clean for agents.
(b) **make the skeleton itself the proof app** — every generated app starts with notes and a
question page an agent must then remove.
(c) **seed the skeleton only**, and accept that step 6 is *sign in* — notes and questions stay
`make demo-ai`'s, and the clickable journey is shorter than §1 says.
*Recommendation: (a).* It keeps §1's journey whole without polluting what agents build on, and a
starter is the natural Phase 1 stand-in for *describe your app*. It is a spec action on §22 and §25.

**2. Split P5.** Everything in §4 is one plan today. Options: one plan in many sittings; or **three
plans, as P4 became P4a/P4b/P4c** —
**P5a, the contract**: public representations, route schemas, OpenAPI under `/v1`, the client,
error-code registry, event schemas and the missing journey events, the API's origin behind the edge
with CSRF and the app-network refusal (and its S6 probe), reserved labels, project creation from a
skeleton and a starter, the slug check API, the missing reads, `LaunchReadiness` view with scan findings persisted,
audience, blueprints and the knowledge pack, admin bootstrap and fleet list. *Acceptance: every §22 step can be driven by a script using only the generated client, with a
session.*
**P5b, delegated tokens and pending actions** (D24): alone, because it is a new credential class and
the authorization suite doubles. *Acceptance: a token runs the whole build loop and is refused the
privileged four, each refusal creating a `PendingAction` a human confirms.*
**P5c, the clients**: `manifest-mock`, `console/` with its boundary, the CI acceptance script.
*Acceptance: 1c's demo — the journey clicked by a person and run headlessly by the script, over one
contract.*
*Recommendation: three plans*, each written after the previous one executes — the 2026-09-04 lesson
that P3 cost eight defects reconciling against an imagined P2 applies with full force to a console
written against an imagined contract.

**3. Where the API lives, and whether app containers may reach it.** §21 puts the separate front-end
at `app.manifest.internal` through the edge *"so cookie scope, CSRF origin and SAML redirect origins
match production"*, and says nothing about the console's origin or the API's. A browser console
needs the API same-origin or behind CORS. Options:
(a) **the API behind the edge at the console's origin** (e.g. `console.manifest.internal`, API under
a path) **with the edge refusing app and sandbox networks for that route** — and S6 gains a probe
proving it; (b) the same without the refusal, amending §16's rule to *"may reach only the public,
authenticated API"*; (c) keep the API on `127.0.0.1:7100` and serve the console with CORS.
*Recommendation: (a)* — it matches §21's reasoning and keeps §16's rule true into Phase 3. It moves
`MANIFEST_CONTROL_PLANE_ORIGIN`, the control plane's SP registration and every script (§2.3).

**4. The public contract's version scheme.** D23.8 says *versioned* and nothing more; the separate
front-end team will build against whatever P5 publishes. Options: a path prefix (`/v1/…`), a media
type or header, or unversioned until a second version exists. *Recommendation: `/v1` path prefix*,
decided now — it is the one choice that is expensive to change after a second team depends on it.

**5. Whether "can a second developer reproduce all of it?" requires the second-machine clean
clone.** §17 asks it of 1c; RUNBOOK's *Known gaps* records that test as never run, for want of a
second Mac. *Recommendation:* decide now whether P5c's acceptance includes it, so the plan does not
end claiming an answer it did not measure.

*Already settled before this brief, and not to be re-opened either:* deploy returns once the new instance serves (P4c R3);
redeploys interrupt nobody (P4c R1–R11); §10's per-user budget is validated, not enforced; live
tailing of an app's own output is not v1 (§14).

## 6. Decisions the plan should make itself — with a default to start from

- **Where the proof app moves:** into the blueprint as its first starter — §25's example path is
  `blueprints/node-ts-mongo/starters/proof-app/` — with `scripts/lib/proof-app.sh`, which today lays
  `fixtures/proof-app` over the skeleton by hand, reading the same starter so the demos and project
  creation cannot disagree about what the proof app is (P4b's reason for `proof-app.sh` existing).
- **Where the new packages live:** `packages/contract`, `packages/mock`, `packages/console` in the
  existing pnpm workspace, each with its own gates wired into the four root commands; the import
  boundary enforced by an ESLint rule **and** a test that reads `console/`'s imports.
- **The schema source of truth:** zod stays the language, through the `zod/v4` API the installed
  package already carries (§2.3) — the plan measures it on one **real** route end to end (Fastify 5
  validation, response serialization, the emitted OpenAPI fragment) before converting the rest, and
  records what `z.toJSONSchema` cannot express.
- **The event stream in the contract:** JSON Schema for frames and event payloads as components of
  the same document, with an `x-` extension or a sibling AsyncAPI file — measured against what the
  mock and the client generator can actually consume.
- **Long-running requests:** R3 keeps deploy synchronous; say so in the contract, set explicit
  timeouts in the client, and decide whether builds follow the same rule. Measure a cold build.
- **CSRF:** an explicit control for cookie-authenticated mutations (Origin check against the
  configured origin, or a double-submit token), with the exempt routes argued one by one.
- **The CI script's credential:** a scripted test-user login through the edge (as `idp-login.sh`
  does), then a delegated token minted through the client — so the script exercises D24 rather than
  bypassing it. Before P5b exists, a session.
- **Public representations:** one module owns them, rows are mapped explicitly, and no field leaves
  that a client should not see (`handle`, `driver`, `resolvedConfig` internals).
- **An error-code registry:** every code enumerated once, exported through the contract, with a test
  that fails when a route throws a code the registry lacks.
- **`LaunchReadiness`:** a resource computed from what exists, each item stating `state`, `owner` and
  `why`, and saying *not built yet (Phase 2)* rather than inventing a status. Persist scan findings on
  the release so the scans item has data.
- **Admin bootstrap:** a script run with the admin database URL that promotes a named user, records an
  audit event, and is documented in RUNBOOK.
- **The demo scripts:** keep them as `curl`, or move them onto the generated client. Either is
  defensible; a third client written by hand is a drift risk, so say which and why.

## 8. Traps from P1–P4c that will bite this plan

- **A plan's own negative controls often cannot fail.** P4c: five of the plan's controls and four of
  its acceptance's nine. For P5 the boundary test, the drift test and the mock validation are the
  load-bearing controls — **write down the edit that must turn each red, and watch it.**
- **The test builds the value; the running system re-derives it** (P3 session 5, seven defects).
  The CI script must run against the platform **through the edge**, never `app.inject`, and the
  console must be clicked against the real platform as well as the mock.
- **A stand-in that is not the real thing produces a real-looking failure** (P4c finding 74, the `nc`
  app). `manifest-mock` is a stand-in by definition: validate it against the document, and never let a
  green run against the mock stand for the platform.
- **Vitest strips types.** A generated client is mostly types; `tsc` over `console/` and the script is
  the only check that it fits.
- **A module with no caller** — shipped four times here. The client's first caller is the script, not a
  unit test.
- **A status is not evidence** (P4b finding 193): the edge's wildcard answers `200` for anything.
- **`app.registeredRoutes` fails the authz suite for an unlisted route** — budget for it on every
  route-adding task.
- **Sittings, one per session**, and a sitting with the network on for dependency additions (P4c
  sitting 7's shape).
- **The sweep is the step that gets forgotten** — ORIENTATION §6 — and P5 adds documents
  (`console/` and `mock/` READMEs) that will state status.
