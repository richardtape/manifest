*Written 2026-09-19, straight after P5c was executed and Phase 1c closed, for the agent that
writes P6a. It compares what §13, §9 and the roadmap ask of Phase 2's first plan with the code as
it stands at `d95d848`, and records what was read and measured that day (§2, §3). §5 holds the

## 1. The requirement

**The roadmap's P6 row:** production environments, promotion by digest, the `LaunchReadiness`
**gate** (1c ships only its read-only view), sensitive-diff escalation, approvals with step-up
re-auth, gate integrity (§13).

**§17's Phase 2 row** puts more in the phase than P6 carries — custom domains (P7), audience tiers'
production effects (P9), showcase and forking (P10), the admin console (P11), IAM package and PIA
draft *generation* (P8). P6 is the first of the six and the prerequisite for P7, P8 and P9.

**§13 is the section to read in full.** Four things it asks for, in its own order:

1. **Promotion never rebuilds.** Production runs the exact digest staging ran.
2. **D19 — first launch is a checklist, not a button.** §13's table names **five** blocking items,
   each with an owner. **The code computes six, or seven** — `computeLaunchReadiness` adds
   `domain` (always, and `met` today) and `load-rehearsal` (only for a `large_course` or `public`
   audience, P9's). The difference is deliberate and predates P6; do not "reconcile" it by
   deleting either. Count carefully in any sentence that states a number.
3. **D9 — the gate.** *First launch* needs the whole checklist; *subsequent releases* are
   self-serve **unless `isSensitiveDiff()` reports a change to one of §7's seven sensitive
   fields**, in which case the release re-escalates — and a change to `auth.attributes`
   additionally requires an IAM change request to reach `active` first (§9).
4. **Integrity of the gate.** Approval binds to an immutable digest and deployment verifies it
   before starting anything; the registry rejects pushes from app and sandbox contexts; the
   approval record is non-repudiable (actor, timestamp, the exact diff shown at decision time);
   approving requires step-up re-authentication (§20); laptop-built images never reach UBC
   infrastructure.

**§13 also states the residual risk, and P6 must not quietly widen it:** the gate reviews
`manifest.yaml`, not code. After first launch, arbitrary code changes reach production unreviewed
and only the seven sensitive fields re-escalate. That is an accepted trade, and the compensating
controls are §20's containment measures.

**The question P6 answers:** *is it safe, and can we get an app legitimately launched?*

## 3. Read and measured on 2026-09-19

Three findings, and the second is the one that will cost a sitting if it is discovered inside a
task rather than here.

### 3.1 The SP side of step-up is available; the IdP side is unmeasured

`@node-saml/node-saml` **5.1.0** — the library the control plane uses — declares
`forceAuthn: boolean` in `lib/types.d.ts:128`. So Manifest can *issue* a `ForceAuthn` AuthnRequest
today.

Whether the Manifest IdP **honours** it is not measured, and this project has been bitten by
exactly this class before: P4a found **four settings that read like controls and are not**,
including two node-saml `want*Signed` options and SimpleSAMLphp's `validate.authnrequest`. The IdP
is SimpleSAMLphp `^2.0` built by `composer create-project` (`infra/idp/Dockerfile:23`), kept
current rather than pinned (§8, *Decided*). **Measure it in Task 1: issue a `ForceAuthn` request
against a browser that already holds an IdP session and assert the person is asked again.** A
step-up that silently reuses the existing session is a step-up that does nothing, and every test
of it would pass.

### 3.2 Making the listener split real is materially harder than "one more alias" — and here is exactly why

Rich decided (§5, decision 3) that P6 makes §12's fail-closed claim testable. The obstacles, read
from the code rather than reasoned:

**(a) The zones are NESTED, and production is the parent.** `config.ts:132-134`:

```
MANIFEST_ZONE_SANDBOX     sandbox.manifest.internal
MANIFEST_ZONE_STAGING     staging.manifest.internal
MANIFEST_ZONE_PRODUCTION  manifest.internal          ← the parent of the other two
```

and `hostnameFor` is `<slug>.<zone>`. dnsmasq's single rule
`--address=/manifest.internal/127.0.0.2` (`infra/compose.yaml:65`) is a **wildcard over the whole
tree**, so it answers for all three zones — *and* for `console.manifest.internal` and
`idp.manifest.internal`, which are in the production zone by name and must stay internal.
Splitting the zone by address therefore moves the console and the IdP onto the public address
unless each gets a more-specific entry. **Any plan that says "point the production zone at the new
alias" is wrong in a way that would take the console down.**

**(b) A port in the URL is not an acceptable fallback.** `infra/compose.yaml:76-78` says so in
terms: *"A PORT IN THE URL WOULD BREAK the parity property §9 needs, so an override port is not an
acceptable fallback here."* So the second listener needs a second **address** on the host — a
second `lo0` alias, `127.0.0.3`, added by the same mechanism `infra/lib/ensure-alias.sh` uses for
`127.0.0.2`. That is `sudo ifconfig lo0 alias`, which **cannot prompt from a tool call** and is
therefore Rich's (CLAUDE.md, *Non-negotiables*). It is additive, Valet is untouched, and
`make host-undo` must remove it too.

**(c) The readiness probe resolves through the CONTAINER side, which answers one address for the
whole zone.** `routing/readiness.ts`'s `curlThroughEdge` starts a throwaway `curlimages/curl`
container on `manifest-platform` with `Dns: ['10.89.0.53']` — dns-containers — which answers
`10.89.0.10` for everything in `manifest.internal` (`infra/compose.yaml:39`). A production app's
readiness probe would therefore arrive at **`manifest-caddy:443`, the internal server**, and find
no route there.

**The good news, and it is the reason this is safe to attempt:** it fails **loudly**, not
silently. `waitForIdentity` refuses a 200 that carries no `X-Manifest-Instance` and says in its own
words *"that is the edge's wildcard, not a routed app"*. So a mis-listenered production deploy
fails its readiness check with an accurate message rather than passing against the wildcard —
which is precisely the trap P4b finding 193 recorded and P4c's identity probe was built to close.

**A mechanism that works, offered as a starting point rather than a decision:** one Caddy
container, two servers — `srv0` on `:443` as today, `srv1` on `:8443` inside the container, mapped
to `127.0.0.3:443` on the host. The browser URL then carries no port (b is satisfied), and the
**probe** targets `:8443` for production only. That is a port in a probe URL, not in a faculty-
facing one, and it should be written down as the divergence it is. The dnsmasq split is then
host-side only: `--address=/manifest.internal/127.0.0.3` with more-specific entries pinning
`staging.`, `sandbox.`, `console.` and `idp.` back to `127.0.0.2`. **Task 1 must measure this
before any task depends on it**, and if it turns out to cost more than a sitting, the fallback is
the option Rich rejected — assert the listener at config level and state the gap — taken
deliberately and recorded, not discovered.

**Also: a `compose.yaml` change recreates `manifest-caddy` and drops every runtime route**, so
every app hostname then answers the wildcard until the control plane reboots (§2's box, and P5c
Decision 4 priced this). Sequence the sitting accordingly.

### 3.3 The coverage gate will not protect P6 from itself

P5c sitting 9 measured that with all 34 operations in `DELIBERATELY_UNCALLED`, `coverage.test.ts`
is **green**, and the `checked > 30` assertion cannot see it because `checked++` runs before the
exemption test. So every route P6 adds needs a console caller **or** an honest entry with a
reason — and **a reviewer must read that list, because the gate will not**. P6 adds enough routes
(approve, reject, step-up, the two external records, the rehearsal) that this is a live risk, not
a formality.

## 5. Decisions Rich made, 2026-09-19

> **ALL THREE ARE DECIDED. Do not re-open any of them.**

**R1. P6 folds in `IamRegistration` and `PrivacyAssessment` as tracked objects with manual state
transitions; P8 keeps the generation.** So the gate blocks on real rows an administrator can
satisfy out of band with a pasted ticket reference, and **P6's demo is an app that genuinely
reaches production**. This is not an invention: §9 already describes *"submitted by a human, with a
ticket reference pasted in"* as the first implementation, and says in terms that the objects are
modelled with submission state *"precisely so that"* the manual and programmatic cases are the same
state transition with a different driver behind it — the source/runtime driver pattern (D5, D10).
*Rejected:* a gate that only ever refuses, which would leave P6's end-to-end path unexercised —
the place this project has found every one of its worst defects; and reordering P8 before P6,
which runs against the roadmap's stated dependency. *Cost:* two tables and two state machines in
P6 rather than P8, and **a roadmap edit** (§7).

**R2. The D21 rehearsal is redefined as a local, production-shaped rehearsal that P6 automates.**
D21 asks for one run against `authentication.stg.id.ubc.ca`, which C1 says this laptop cannot
reach. P6 instead deploys the candidate digest into the production environment behind the gate,
registers its SP with production-shaped values (the production entityID, the public-listener
hostname, the registered attribute set), completes one real CWL sign-in against the Manifest IdP,
and records pass/fail with evidence on the project. The item becomes met by a **measurement**
rather than a checkbox. §9's real-Shibboleth run remains an external-track obligation.
*Rejected:* a third administrator checkbox, which would make three of six blocking items human
assertions and weaken the thing `readiness.ts` was deliberately built to be; and a waiver
mechanism, which is the exact hole §13's *Integrity of the gate* exists to close. **Required:** the
item's own `why` text must say that the rehearsal proves the registration's SHAPE and never UBC's
acceptance of it, so nobody mistakes one for the other.

**R3. P6 makes the internal/public listener split real.** §12 chose listener assignment over IP
allowlisting *because* it fails closed — *"a misconfigured allowlist leaks quietly, whereas a route
bound to the wrong listener is simply unreachable"* — and on the only machine that exists that
claim has never been watched failing. P6 is the first plan to put anything on the public listener,
and P7's custom domains are *"production-only, and only on the public listener"*, so the cost is
paid now or paid later with more built on top. *Rejected:* keeping §21's divergence 2 and asserting
the listener at config level only; deferring to P7. **See §3.2 for what this actually costs — it
is the highest-risk item in the plan, and its Task 1 measurement gates the tasks that depend on
it.**

## 6. Decisions the plan should make itself — with a default to start from

Each of these is the plan author's, in the sense ORIENTATION §6 rule 5 means. The default is what
I would start from; record the reasoning and what changing course would cost.

1. **Where the gate is evaluated.** *Default:* one function in `launch/`, called by both the deploy
   route and the read, so the view and the gate can never disagree. P5c sitting 6 measured the two
   paths **byte-identical** today; keep that property and assert it.
2. **What a `diff_snapshot` stores.** *Default:* the rendered diff at decision time, stored — not a
   reference that would be recomputed later against a changed spec. §13 says *"the exact diff shown
   at decision time"*, and a recomputed diff is a different claim.
3. **Where the AI summary comes from, and what happens when it cannot be produced.** *Default:*
   `ai/`'s existing LiteLLM path, and **a failed summary does not block an approval** — it is
   recorded as absent. An approval gate that fails closed on a language model being down is an
   outage, not a control. Say so in the record.
4. **How `steppedUpAt` survives a stateless cookie.** *Default:* reissue the session cookie with
   the claim after the `ForceAuthn` callback, and give it a short freshness window enforced at
   assert time. Note the consequence honestly: like every Phase 1 session property, it cannot be
   revoked before expiry (§20).
5. **Whether step-up guards `members:manage` from day one.** *Default:* yes — §20 names it, the
   route exists, and adding it later means a second pass over a route P5b already tested. It also
   gives step-up a caller that is not new, which makes the negative control cheaper.
6. **Whether the rehearsal is re-runnable and what invalidates it.** *Default:* re-runnable, and
   invalidated by a change to `auth.attributes` or to the registered SP values — otherwise a
   rehearsal passed in week one certifies a registration that changed in week six.
7. **Whether an approval is invalidated by a new build.** *Default:* yes, necessarily — the
   approval binds a digest, so a new digest has no approval. State it, because it reads as a bug
   the first time somebody meets it.

## 8. Traps from P1–P5c that will bite this plan

Chosen because P6's shape invites each one specifically.

- **A green result is not evidence a control is in force**, and a plan's own negative controls
  often cannot fail. P4c measured five of its plan's and four of its acceptance's nine as
  unfireable; P5b had one in every sitting from the second to the seventh. **P6 is a plan almost
  entirely composed of refusals** — that is the worst possible ground for this trap. Every refusal
  asserts its CODE, never its status: P5a sitting 6's lesson, reproduced live four times since.
- **The edge's wildcard answers 200 for any name in the zone.** With production routes on a new
  listener, a status-only check cannot tell a working production app from the wildcard, from
  staging, or from nothing. Use `waitForIdentity` and assert `X-Manifest-Instance`.
- **F16, the newest and the sharpest.** P5c's logout fix passed every test and was still broken
  against the real IdP, because **every test fired garbage at the route and asserted a refusal —
  and a route that refuses everything passes them all.** P6's step-up route is exactly that shape.
  A refusal test needs a positive control in the same file.
- **A negative claim needs a positive control in the same test.** P5b sitting 6: two of four new
  tests were *"is not limited"* claims, which are true of a platform that limits nothing. *"This
  release is not blocked"* is the same shape.
- **`.map(fn)` passes the array index as a second argument** (P5b sitting 7). Any representation
  mapper that grows an optional `now` or `actor` parameter will silently receive `0`.
- **Vitest strips types; `pnpm typecheck` is the only gate that sees a whole class of error**, and
  `exactOptionalPropertyTypes` makes that class common. Two of P5c's findings were caught by `tsc`
  alone.
- **A swallowed `.catch(() => undefined)` is this codebase's most productive defect.** Use
  `console.error`; `request.log` writes nothing here.
- **`pnpm test` truncates the control plane's tables** and `pnpm test:docker` restarts the edge,
  drops every runtime route, re-registers the platform's SP row and regenerates seven dead app
  networks and one volume. **Restart the control plane afterwards.** P6 touches `routing/`,
  `releases/`, `sso/`, `infra/` and `projects/`, so the Docker tier is **owed by almost every
  sitting** — budget the 13 minutes rather than being surprised by it.
- **`POST /v1/projects/{id}/members` answers `400 MEMBER_USER_NOT_FOUND` for anybody who has never
  signed in to MANIFEST** — signing in to a deployed app is a different SP with a different user
  store (P5c sitting 9, F14). Any clicked run that needs a second person needs that sign-in first,
  in an incognito window.
- **The extension's per-site permission on `idp.manifest.internal` is intermittent** (P5c F15). A
  clicked run must be able to proceed blind across the IdP hop, reading the tab's title. Step-up
  makes this worse, not better: it adds a *second* IdP hop per privileged action.
- **Measure a plan's premises, not just its steps** (P5c sitting 9, F1). Task 14's premise about
  three machine states was simply false, and three runs proved it.

## 10. The cut — P6a and P6b, agreed by Rich on 2026-09-19

**Two plans, split on D9's own two clauses.** D9 already reads *"1. First launch to production…
2. Subsequent releases…"*, and each half demos on its own, which is the roadmap's bar for a plan.

### P6a — the first production launch

The second listener made real; production deploys by verified digest; the three remaining
readiness items made satisfiable (the two external records, the rehearsal, admin approval with
step-up); the gate that blocks; gate integrity.

**Demo:** an app reaches production for the first time — and every one of D19's five blocking items
is honestly met, not waived.

**Its Task 1 is measurements, alone and first**, as every plan since P4c. The three that must be
bought before anything depends on them: whether SimpleSAMLphp honours `ForceAuthn` (§3.1); what a
second Caddy server and a second alias actually cost on this machine, including the dnsmasq split
and the probe path (§3.2); and whether `computeLaunchReadiness`'s items survive being read by
something that blocks rather than displays.

### P6b — subsequent releases

Self-serve redeploys to production; `isSensitiveDiff` given its caller at last; the `diff_snapshot`
with its AI summary; re-escalation; and the `auth.attributes` → IAM change request path.

**Demo:** a self-serve production redeploy, then a sensitive change that re-escalates and is
refused until an administrator approves it.

### Rules that survive any re-cut

Three, and they are the ones this project has paid for:

- **Task 1 stays first and alone.** It has moved task boundaries in three of the last four plans
  and closed a four-plan-old open question in one of them.
- **The acceptance stays alone and last**, and it is the plan's own task — not something that
  happens after the last feature.
- **P6a's listener work is sequenced early enough that a `compose.yaml` change dropping every
  runtime route is cheap**, and late enough that its Task 1 measurement has landed.

**Sitting count is Rich's**, as it has been for every plan since P4a, and it should be proposed
with its cost stated once the task list exists — not guessed here. On the last three plans' grain,
P6a looks like nine to twelve sittings and P6b like five to seven.
