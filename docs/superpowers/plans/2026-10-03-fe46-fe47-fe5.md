**Goal:** A faculty member's launch records go to **the Manifest team** (at UBC, LTIC), not straight to UBC. **The owner sends** the
privacy assessment, with an answer to every gap only they can fill, and each IAM registration, from Manifest; the record is `sent` and
says who has it and since when. **The team is emailed** — and for every sign-off request too — with nothing a person wrote in it. **An
administrator records that the team submitted it** to the Privacy Office or UBC IAM, with UBC's reference and the day, **or hands it back**
to the owner. **After launch, the owner asks for a change** to a live registration the same way, and the team files it with UBC IAM as a
change request (FE-47). **A question an agent raises names what it would act on** — who, in what role, which release, where (FE-5) — and
**its event carries when it stops waiting** (FE-53).

It is proved by **`make demo-launch`** and **`make demo-token`**, extended, on either driver, through `@manifest/contract`, with the
team's emails read back from Mailpit. A person clicks it too.

**Architecture:**
- **One new state, `sent`, on both records**, between `draft` and `submitted`. The owner's send takes a record to it; only the team's two
  administrator operations take it out — `submit…` (to `submitted`, or for a change to `change_requested`) and `return…` (back to the
  state it was sent from, held in `sent_from`). The generic record routes never move into or out of `sent`.
- **The owner's operations are new: `sendIamRegistration` and `sendPrivacyAssessment`.** **`submitIamRegistration` and
  `submitPrivacyAssessment` keep their names and paths and become the team's** (`launch:record`, an administrator's): the verb now matches
  the state each moves to. **`returnIamRegistration` and `returnPrivacyAssessment`** are the hand-back.
- **The platform's first outbound email** is sent with **nodemailer**, pinned exactly, behind a `Mailer` in a new module, `mail/`. A send
  is told to the team AFTER the commit, in the background, bounded, and an undelivered one leaves an operator line and changes nothing else.
- **The assessment's gaps gain stable ids** (`{ id, text }`), and the send carries `answers[] { gapId, answer }`, every gap exactly once.
- **FE-5 is one optional field on a route definition, `pendingObject`**, required by a test of every route whose capability is privileged,
  and run only when D24's refusal happens. The object is stored inside the existing `payload` jsonb, so there is no migration.

## Read this first — what this plan knows from the code

*Read at `8def435` on 2026-10-03 by this session and two read-only surveys. Task 1's `[M1]` re-reads every one; a fact a later measurement owns says which (T1: M<n>).*

**The records, as they are.**
1. **The states are Postgres enums**: `iam_registration_state` (`draft`, `submitted`, `active`, `change_requested`, `expired`;
   `db/schema.ts:665-671`) and `privacy_assessment_state` (`draft`, `submitted`, `approved`; `:678-682`), created by migration
   `0019`. **No migration in this repository has ever added a value to an existing enum** (`grep "ADD VALUE" drizzle/*.sql` is empty).
2. **drizzle runs EVERY pending migration inside ONE transaction** (`drizzle-orm@0.45.2`'s `pg-core/dialect.js:44-70`,
   `session.transaction(async (tx) => { for … })`), and migrations are applied by `drizzle-kit migrate`, never at boot. **Postgres refuses
   to USE an enum value added in the same transaction** (*"unsafe use of new value"*). So a CHECK written `state = 'sent'` beside the
   `ADD VALUE` would fail the migration — and on a fresh database every migration from `0000` runs in that one transaction. *(T1: M2)*
3. **`iam_registrations`** (`db/schema.ts:691-805`): `change_requested_from` text with a CHECK both ways (`:751`, `:799-802`);
   `submitted_at`/`submitted_by` (`:~766-768`), described as *"stamped by the owner's "I've sent it" … by an administrator's record that
   moves the registration into `submitted`, and by filing a change request"*. **`privacy_assessments`** (`:807-826`): the same pair.
4. **The machines are tables**: `IAM_ARROWS` and `PIA_ARROWS` (`launch/transitions.ts:39-54`) are the generic record routes' arrows — an
   administrator may move `draft → submitted` directly, and P6a's and P6b's demos do (`journey/src/production.ts:497-501`,
   `releases.ts:625-627`). `SUBMIT_ARROWS` (`:103-106`) is the owner's set: a registration from `draft`, `change_requested` or `expired`;
   an assessment from `draft`. **`change_requested` is sendable whatever `change_requested_from` says** — a change request an
   administrator FILED with UBC included, though the set's own comment says *"again once UBC has asked for changes"*.
5. **The owner's *"I've sent it"*** is `submitIamRegistration` (`launch/records.ts:565-676`) and `submitPrivacyAssessment` (`:682-737`): in
   one transaction, the record `FOR UPDATE` and what gates it `FOR SHARE` (`:555-560`); draft required; `SUBMIT_ARROWS`; UBC's order
   (`LAUNCH_PIA_NOT_APPROVED`, `LAUNCH_STAGING_NOT_REGISTERED`, `:592-619`); the draft read (`LAUNCH_DRAFT_CHANGED`, `:486-495`); the PIA
   number in the package (`LAUNCH_DRAFT_STALE`, `:629-636`); a day the person names (`sentDay`, `:502-528`, `LAUNCH_SENT_AT_INVALID`); then
   `iam_registration.submitted` / `privacy_assessment.submitted` after the commit. **The routes** (`api/routes/launch.ts:360-456`) are
   `credential: 'session'`, `capability: 'launch:submit'`, body `SubmitLaunchRecordRequest { sentAt?, reference?, draftGeneratedAt? }`

## Decisions this plan makes, and why

1. **THE CONTRACT GOES TO `1.8.0` ONCE, AT TASK 2**, the first schema change; Tasks 4–8 add to it. **A minor, with the breaks stated**
   in the version's description and the front-end's message — the faculty-ready plan's `1.6.0` precedent (*"a minor, with the break
   stated"*). The breaks: `submitIamRegistration` and `submitPrivacyAssessment` become an administrator's, with a new body;
   `SubmitLaunchRecordRequest` is retired; `PrivacyAssessmentDraft.sections[].gaps` becomes `{ id, text }[]`; two enums and the queue's
   kinds gain values. *Rejected:* `2.0.0`, which the front-end would read as every operation moving. *Rejected:* a bump per task. *Cost to
   change course:* the version string.
2. **THE OPERATIONS.** **`sendIamRegistration`** and **`sendPrivacyAssessment`** (the owner's, `launch:submit`, person-only, new paths
   `…/send`); **`submitIamRegistration`** and **`submitPrivacyAssessment`** keep their names and paths (`…/submission`) and become **the
   team's record**, `launch:record`; **`returnIamRegistration`** and **`returnPrivacyAssessment`** (`…/return`, `launch:record`, no body)
   are the hand-back. Each verb names the state it moves to — the names the front-end's F5b plan already proposed for the owner
   (*sendPrivacyAssessment, sendIamRegistration*). No client outside this repository calls the submits yet (the front-end's F5b sends wait
   for this plan; `grep` of `~/Developer/manifest-app/packages` is empty).
   - *Rejected:* **the team's step through `recordIamRegistration`** with `state: 'submitted'`. That route needs the whole registration in
     its body to say *"submitted, ticket X"*, and a hand-back's target is the row's `sent_from`, which no static arrow can express.
   - *Rejected:* one team route with an `outcome` field. A refusal's code would then depend on a field, and the matrix doubles.
   - **`launch:submit` keeps its name**, re-described as *sending a launch record to the Manifest team*. Renaming a capability reaches the
     authorization matrix, D24's list and the person-only set for no change in who holds it.
   - *Cost to change course:* operation names are the generated client's; renaming later is a break of its own.
3. **THE OWNER'S SEND HAS NO DAY: it is the moment of the send** (`sent_at = now`), because it is made in Manifest. **The team's record
   carries the day the team sent it to UBC** as `sentAt` (`YYYY-MM-DD`, today in Vancouver when absent; not after today; not before the
   owner's send), and **a required `reference`** (UBC's: the PIA number, or IAM's ticket), 1–100 characters. The field keeps the name
   `sentAt` and the refusal keeps `LAUNCH_SENT_AT_INVALID`: it is still *the day it was sent to UBC*, and no code is retired.
   `draftGeneratedAt` stays on the owner's send, optional, as today.
   - *Rejected:* an optional reference. §9 says the team records *"with UBC's reference and the day"*, and the queue's with-UBC item names
     the ticket.
4. **THE GENERIC RECORD ROUTES NEVER MOVE INTO OR OUT OF `sent`** (`LAUNCH_TRANSITION_INVALID`, naming the team's two operations). Every
   other arrow they have stays, **the administrator's `draft → submitted` included**: it is how an administrator records a submission made
   without a send in Manifest, and P6a's and P6b's demos and their tests record that way. *Rejected:* removing it — every record through
   the owner's send, which rewrites `make demo-production`'s and `make demo-releases`'s recorders and their tests for no rule a person
   meets. *Cost to change course:* one arrow, and those recorders. **Rich's (a), 2026-10-03.**
5. **AN OWNER SENDS FROM `change_requested` ONLY WHEN UBC ASKED THEM FOR CHANGES** (`change_requested_from = 'submitted'`). A change request
   the team FILED with UBC (`from: 'active'`) is UBC's to answer: drafting and sending are refused (`LAUNCH_RECORD_SUBMITTED`, as for a
   `submitted` record). This is what `SUBMIT_ARROWS`' own comment says (*Read this first* 4), and it is what makes a hand-back's target
   well-defined: **a registration sent from `change_requested` and handed back returns to `change_requested` with
   `change_requested_from: 'submitted'`** — the owner's move again. *Rejected:* storing the origin's origin. **Rich's (a), 2026-10-03**,
   though today's code lets an owner say *"I've sent it"* over a filed change request.
6. **WHAT A SEND LEAVES BEHIND.** `sent_from` is set on entering `sent` and cleared on leaving it (a CHECK both ways, as
   `change_requested_from` has). **`sent_at`, `sent_by` and `gap_answers` are the LAST send's**, kept after the record leaves `sent` and
   replaced by the next send — history, as `submitted_at` is today. The checklist and the queue read them only while the state says the
   team has it.
7. **THE MIGRATION ADDS THE ENUM VALUES WITH `ALTER TYPE … ADD VALUE 'sent' BEFORE 'submitted'`, AND EVERY CHECK THAT NAMES `sent`
   COMPARES `state::text`** — so the migration never uses the new value inside drizzle's one transaction (*Read this first* 2). Task 1's
   `[M2]` proves both halves in a throwaway Postgres. *Rejected:* recreating the type (rename, create, `ALTER COLUMN … USING`), which
   drizzle-kit does not generate and which locks both tables. *Rejected:* text columns with CHECKs instead of enums, which changes every
   reader's type for a migration's convenience.
8. **THE GAPS' IDS ARE SEMANTIC AND STABLE**: `<section>.<what>` — `collected.app-data`, `stored.staging-cover`,
   `flows.classification`, `flows.unknown-model`, `retention.removal` (or `retention.declare` when none is declared), `retention.disposal`,
   `accountable.platform-contact`, `accountable.breach`, `hosting.production`, `hosting.offshore-ai`, `hosting.repository` (Task 4 reads the
   exact list from `assessment.ts`). The same gap keeps its id across drafts, so a front-end's suggested answer survives a re-draft. **A
   stored draft from before this plan** is read with ids `<section>.<n>` (its index), which are stable for that draft because it is never
   regenerated in the old shape. *Rejected:* refusing an old draft — an approved assessment's draft is what it was approved from, and the
   record must still show it.
9. **THE ANSWERS.** `answers: { gapId, answer }[]` — at most 64; each answer 1–2,000 characters (the front-end assumed 2,000 *"until it
   says"*); **every gap of the draft read exactly once**, trimmed and non-blank; *"does not apply"* is ordinary text. ONE refusal,
   **`400 LAUNCH_GAP_ANSWERS_INVALID`**, whose message names the missing, unknown, repeated and blank ids. Kept as `gap_answers` in the
   draft's gap order. *Rejected:* answers saved as the owner types (the front-end keeps its own drafts of them; §9 keeps *"what the owner
   sent"*).
10. **THE MAILER IS `nodemailer`** (Rich, 2026-10-03, over the hand-written client this plan first proposed), **pinned EXACTLY** in
    `packages/control-plane/package.json` at the release current on the day of the add — C6's rule (*"pins exactly (never a range)"*),
    which ORIENTATION §3 applies to every app-side dependency — with the version, the day and the reason recorded in the sitting's record
    and the commit. **One networked add** (Task 3's Step 1), and **`@types/nodemailer`**, a devDependency, exact, under the same yes, only
    if the release ships no types. Its transport sets every timeout to **10 s** (nodemailer's defaults are minutes) and
    `disableFileAccess` and `disableUrlAccess` (Manifest attaches nothing, and a message must never read a file or fetch a URL). **UBC's
    relay** — `smtps:`, credentials, `requireTLS` — is configuration nodemailer already has (Decision 13), unexercised until the external
    track. *Rejected:* the hand-written client, by Rich's answer. *Cost to change course:* `mail/index.ts`'s `smtpTransport`; `Mailer` is
    the seam.
11. **THE EMAIL IS TOLD, NEVER AWAITED.** `mailer.tellTeam(notice)` is called AFTER the commit and after the event; it starts nodemailer's
    `sendMail` in the background, tracked in an `inFlight` set (`releases/build.ts`'s pattern), bounded by the transport's 10 s timeouts.
    A failure writes ONE operator line — `{ level: 'error', msg: 'the Manifest team could not be emailed; the queue still holds the item',
    notice, projectId, error: <nodemailer's code> }`, never its message or the server's answer, which can carry an address — and changes
    nothing else. **No retry and no outbox**: §26 says *"the queue is the record, and the email is how the team hears of
    it"*. `settled()` lets a test, and shutdown, wait for what is in flight. *Rejected:* awaiting the send inside the request, which makes
    an owner's send as slow as the relay.
12. **THE EMAIL'S WORDS ARE FIXED SENTENCES OVER IDS AND NAMES**: which app (its name and slug), what was sent or asked, by whom (the
    sender's display name), when, and two links — the item (`/projects/{id}/records` or `/releases/{releaseId}/approval`) and `/queue`, on
    `config.sp.origin`. **Never a draft, an answer, an attribute list, a note, or a reason.** nodemailer composes the message: it encodes a
    non-ASCII subject as RFC 2047 and the plain-text body as UTF-8 with a transfer encoding it chooses. **Manifest's half**: the subject
    has every CR and LF replaced by a space before it is handed over (`oneLine`), whatever the library also does; the message is text only,
    no `html` and no attachment; `From` and `To` are configuration, never a person's words. *Why:* a project name is a person's words, and
    header injection is the one way they could change an email's meaning. The tests assert what the composed message — and Mailpit — hold.
13. **CONFIGURATION, WITH THE LAPTOP'S DEFAULTS**: `MANIFEST_SMTP_URL` (default `smtp://127.0.0.1:7111`; `smtp:` or `smtps:`, a host and
    an explicit port, and `user:password@` when a relay wants `AUTH` — a secret, so a refusal never repeats the URL; else
    `CONFIG_INVALID`), `MANIFEST_SMTP_REQUIRE_TLS` (`0` or `1`, default `0`: nodemailer's `requireTLS`, STARTTLS or refuse),
    `MANIFEST_TEAM_EMAIL` (default `team@manifest.internal`; one address, checked as
    `MANIFEST_LAUNCH_CONTACTS` checks one) and `MANIFEST_MAIL_FROM` (default `Manifest <manifest@manifest.internal>`). Documented in
    `.env.example` and RUNBOOK. **No new `make doctor` or `make verify` check**: the default target is the one `make verify` already
    round-trips, and the demo reads the control plane's own emails back. *Rejected:* a required address, which every unit test's server
    would have to supply.
14. **`mail/` IS A MODULE OF ITS OWN** (`index.ts`, `team.ts`, `testing.ts`), reached through its `index.ts`
    (`module-boundaries.test.ts`), and **the only file that imports `nodemailer`**. `ServerDeps` gains `mailer: Mailer`;
    `createMailer(config, transport?)` takes the transport as a parameter, so a test hands it nodemailer's own `streamTransport` — the real
    composer, sending nothing — or a transport that fails; `api/testing.ts`'s servers get `recordingMailer()`, so the unit tier's servers
    open no socket. **Its first caller is the sign-off request** (Task 3); the sends are its second (Task 5).
15. **FOUR NEW EVENT TYPES**: `iam_registration.sent` `{ environment, sentFrom }`, `privacy_assessment.sent` `{ gapCount }`,
    `iam_registration.returned` `{ environment, to }`, `privacy_assessment.returned` `{ to }`. **`…submitted` moves to the team's record**:
    its `sentAt` keeps its name and now means the day the team sent it to UBC, and `iam_registration.submitted` gains **`changeRequest:
    boolean`** (true from Task 7, when the team files a change). Counts, never the answers or the attributes (`recorded`'s rule, `launch/
    records.ts:317-321`). The reason for a hand-back travels outside the record, as UBC's questions do (FE-46's *Not asked here*).
16. **THE QUEUE'S NEW KINDS**: `iam-registration-to-submit`, `iam-change-to-file` (Task 7) and `privacy-assessment-to-submit` — what the
    team does next — ordered after `release-approval` and before the three with UBC. Their `since` is `sent_at` and `requestedBy` the
    sender. The with-UBC items' `requestedBy` becomes `sent_by ?? submitted_by`: the person who asked, not the administrator who recorded.
17. **NO NEW FIELD ON A CHECKLIST ITEM.** `since` dates the wait (`sent_at` while `sent`; `submitted_at` while with UBC), its `why` names the
    holder, and the record's `state` is how a client tells who has it (the front-end reads no step's words from prose, FE-9). *Rejected:*
    `waitingOn: 'owner' | 'team' | 'ubc'`. *Cost to add later:* one additive field.
18. **FE-5'S OBJECT IS A TYPED UNION, DECLARED BY THE ROUTE** — `pendingObject?: ({ deps, params, body }) => Promise<PendingObject>` on
    `RouteDefinition`, run only in the wrapper's refusal branch, stored as `payload.object`:
    - `{ kind: 'member', person, role }` (addMember), `{ kind: 'member-removal', person }` (removeMember), `{ kind: 'deploy', release: { id,
      commitSha }, environment: { id, kind } }` (deploy).
    - **A person is named exactly as the request named them** — `{ namedBy: 'puid' | 'cwlLogin' | 'email' | 'userId', value }` — **and by
      name only when they are already a member of this project** (`member: { userId, displayName } | null`). *Why:* the 403 that creates the
      question carries it, and so does `getPendingAction` on the token; resolving a login or an email for a person who is NOT a member
      would answer the token *"who has signed in"* — the exact enumeration `addMember` orders its checks to prevent (*Read this first* 23). A
      member's name the token can already read from `listMembers`. The draft's Decision 2 (*"by name when the platform knows them"*) is
      narrowed to that; the spec's applied words — *"the person as the request named them"* — are kept exactly.
    - **A deploy's `commitSha` only when the release is the environment's project's**; otherwise null.
    - **"Never a secret" is held by construction**: the union has no free-form field, and no privileged operation takes a secret.
    - **`api/contract/pending-object.test.ts` refuses a route whose capability is privileged and declares no `pendingObject`**, so the next
      privileged route cannot forget it.
    - Old rows read `object: null`. *Rejected:* a summary sentence alone (FE-5's whole complaint), and resolving names for anyone.
19. **ONE STATEMENT OF THE OBJECT'S SHAPE**: the zod schema `PENDING_OBJECT` lives in `observability/event-schemas.ts` (the event carries
    it, and `observability/` cannot import `tokens/` or `api/`); the contract registers it as `PendingObject` from there; `db/schema.ts`
    declares the column's TypeScript shape (`PendingObjectColumn`, `DiffSnapshotColumn`'s precedent), and `tokens/pending.test.ts` holds
    the two equal with `expectTypeOf(…).toEqualTypeOf(…)`, so `pnpm typecheck` refuses a drift.
20. **FE-53: THE EVENT CARRIES BOTH ENDS, AND WHO MINTED THE TOKEN** — `expiresAt` (the question's own: never later than its token's),

    `Token.mintedBy`; Rich, 2026-10-03, 15:09). The question's is what a front-end caps its wait at; the token's is what m130 asked for and what m131's
    fix reads. Both are facts the platform already holds.
21. **FE-47'S CHANGE**:
    - `DRAFTABLE` gains `active`, and a registration drafted from `active` is drawn from **the newest valid manifest, for either
      environment** — the release serving staging cannot ask for the new attribute, because its build fails until UBC registers it.
    - **The attributes asked for are the package's** — `requested_attributes` is set from the package at the send, and the send carries no
      list of its own (one statement of one fact; the existing record's hint already says *"every attribute the app will ask for"*).
    - **A change that asks for nothing new is refused**: `409 LAUNCH_CHANGE_EMPTY` when the package's attribute set, ACS and SLO all equal
      what UBC registered.
    - **The team files it**: `sent` (from `active`) `→ change_requested`, `change_requested_from: 'active'`, `submitted_at` the team's day,

## Review Focus

**The six failure modes most likely to bite a person, that no task's happy path exercises.** Each has its test in the owning task.

1. **A wait counted against the wrong holder, or twice.** An owner sends, the team hands it back, the owner sends again. Expected: **one
   queue item, not two; its `since` and the checklist's are the SECOND send's; `sent_from` is the state it was sent from both times; the
   second send's answers replace the first's.** And a record the team submitted reads `since` from the team's day, never the owner's send.
   Owned by Task 5's *a hand-back and a second send* and Task 6's *since follows the holder*.
2. **An email that leaks, breaks, or holds the owner up.** A project named with a newline, and one named *"Chimie générale"*; an answer
   carrying a marker string; Mailpit stopped; an SMTP server that accepts the connection and never answers. Expected: **the subject is one
   header line, readable in UTF-8; no email contains the marker, a draft's text or an attribute; with Mailpit stopped the send still
   answers `200` and stderr holds one operator line; with a silent server the send answers at once and the line arrives within 10 s.**
   Owned by Task 3's *the message* and *the mailer's failures*, and Task 5's *the send's email*.
3. **An answer set that is wrong in a way a form makes easy.** A gap missing; an unknown id (a draft re-made since, whose ids changed); an
   id twice; a blank or whitespace answer; 2,001 characters. Expected: **`400 LAUNCH_GAP_ANSWERS_INVALID` naming each id, and nothing
   written**; *"does not apply"* accepted. Owned by Task 5's *the answers*.
4. **A registration that reads as registered when it is not, or as unregistered when it is.** A lapsed production registration sent again
   (`expired → sent → submitted`); a live one with a change asked for (`active → sent`). Expected: **the lapsed one keeps a launched app's
   production deploys refused until it is recorded `active`; the live one keeps a release it covers `met` throughout, while a build that
   asks for the new attribute is still refused, naming the team.** Owned by Task 6's *the live registration through sent* and Task 7's
   *the build still refuses*.
5. **A way around the team's step.** An administrator's `recordIamRegistration` from `sent` straight to `active`; a token on any of the six
   operations; a collaborator's send; the team's submission of a record that is not `sent`; a second send over a `sent` record; a send over
   a change request the team filed. Expected: **`409 LAUNCH_TRANSITION_INVALID` (or `LAUNCH_RECORD_SUBMITTED` for the filed change), `403
   TOKEN_CREDENTIAL_REFUSED` for every token, `200` for the collaborator, and nothing written by any refusal.** Owned by Task 5's matrix and
   Task 7's *a filed change is UBC's*.
6. **A question that tells an agent who has signed in.** A token asks to add a person by a CWL login that exists but is not a member, and
   by one that does not exist. Expected: **both questions read alike — `member: null`, the login as the request named it — and the 403's
   body and `getPendingAction` say nothing more**; a person who IS a member is named. Owned by Task 2's *the object never answers who has
   signed in*.

    tellTeam(notice: TeamNotice): void

   * STARTTLS and AUTH are UBC's relay's (Decision 13), configured and unexercised on the laptop.

    return nodemailer.createTransport({
      host: mail.smtp.host,
      port: mail.smtp.port,
      secure: mail.smtp.secure,
      requireTLS: mail.smtp.requireTLS,
      ...(mail.smtp.auth === null ? {} : { auth: mail.smtp.auth }),
      connectionTimeout: 10_000,
      greetingTimeout: 10_000,
      socketTimeout: 10_000,
      disableFileAccess: true,
      disableUrlAccess: true,
    })

    config: Pick<Config, 'mail' | 'sp'>,
    transport: Pick<Transporter, 'sendMail'> = smtpTransport(config.mail),
  ): Mailer {
    const inFlight = new Set<Promise<void>>()
    return {
      tellTeam(notice) {
        const { subject, text } = teamEmail(notice, config.sp.origin)
        const sending: Promise<void> = transport
          .sendMail({ from: config.mail.from, to: config.mail.team, subject: oneLine(subject), text })
          .then(() => undefined)
          .catch((error: { code?: unknown }) => {
            // WRITTEN, NEVER SWALLOWED — and only the code: a message or a server's answer can carry an address.
            console.error(
              JSON.stringify({
                level: 'error',
                msg: 'the Manifest team could not be emailed; the queue still holds the item',
                notice: notice.kind,
                projectId: notice.project.id,
                error: typeof error?.code === 'string' ? error.code : 'SMTP_FAILED',
              }),
            )
          })
          .finally(() => inFlight.delete(sending))
        inFlight.add(sending)
      },
      async settled() {
        await Promise.all([...inFlight])
      },
    }
  }

  export interface GapAnswer { gapId: string; answer: string }
  export const ANSWER_MAX = 2_000

  /**
   * EVERY GAP OF THE DRAFT READ, ANSWERED ONCE (§9; Rich's (ii)): trimmed, non-blank, at most ANSWER_MAX —
   * "does not apply" is an answer. Refused as one, naming every id at fault; answered in the draft's order.
   */
  export function checkGapAnswers(
    draft: PrivacyAssessmentDraft,
    answers: readonly GapAnswer[],
  ): GapAnswer[] {
    const ids = draft.sections.flatMap((s) => s.gaps.map((g) => g.id))
    const given = new Map<string, string>()
    const fault = { unknown: [] as string[], repeated: [] as string[], blank: [] as string[], long: [] as string[] }
    for (const { gapId, answer } of answers) {
      const text = answer.trim()
      if (!ids.includes(gapId)) fault.unknown.push(gapId)
      else if (given.has(gapId)) fault.repeated.push(gapId)
      else if (text === '') fault.blank.push(gapId)
      else if (text.length > ANSWER_MAX) fault.long.push(gapId)
      else given.set(gapId, text)
    }
    const missing = ids.filter((id) => !given.has(id) && !fault.blank.includes(id) && !fault.long.includes(id))
    const said = [
      ...(missing.length === 0 ? [] : [`no answer for ${missing.join(', ')}`]),
      ...(fault.blank.length === 0 ? [] : [`a blank answer for ${fault.blank.join(', ')}`]),
      ...(fault.long.length === 0 ? [] : [`an answer over ${ANSWER_MAX} characters for ${fault.long.join(', ')}`]),
      ...(fault.repeated.length === 0 ? [] : [`more than one answer for ${fault.repeated.join(', ')}`]),
      ...(fault.unknown.length === 0 ? [] : [`answers for gaps this draft does not have: ${fault.unknown.join(', ')}`]),
    ]
    if (said.length > 0)
      throw new LaunchRecordError(
        'LAUNCH_GAP_ANSWERS_INVALID',
        `the privacy assessment's gaps were not each answered once: ${said.join('; ')}`,
        'Answer every gap of the draft you read, once each, by its id — "does not apply" is an answer.',
      )
    return ids.map((gapId) => ({ gapId, answer: given.get(gapId)! }))
  }
