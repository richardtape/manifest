## 1. The requirement

**Rich, 2026-09-14:** a redeploy must not interrupt the app — *the new instance ready before
the edge route moves, an atomic move, a drain, and only then the old instance's AI key
revoked and its container retired.* **Placed** straight after P4b and before P5, so the
generated contract and the console describe redeploys as they will be. **The guarantee
belongs in the §11 `Driver` contract**, so Phase 5's UBC driver inherits it rather than
`deployRelease` alone providing it.

What P4b already did toward it: `deployRelease` mints the new AI key before the instance
starts and commits it only once the instance is healthy (Rich's interim decision, same day).

## 2. What a redeploy does today, step by step

Read from the code on 2026-09-15 (HEAD after P4b). Paths are under
`packages/control-plane/src/`.

1. **`POST /environments/:environmentId/deploy` → `deployRelease`** (`releases/release.ts`):
   binds services, registers the Service Provider, reads the app's secret set, **mints the AI
   key** (`release.ts:416`).
2. **`driver.ensureInstance(spec)`** (`release.ts:450`) → **`DockerDriver.ensureInstance`**
   (`runtime/docker/driver.ts:319`):
   1. ensures the app network (plus `manifest-litellm` for an app with models), the egress
      proxy, and the image in the daemon;
   2. **`ensureInstanceContainer`** (`runtime/docker/instances.ts:130`). The container is named
      `mf-<slug>-<env>-<release8>-app` (`runtime/driver.ts`, `instanceName`). **Same name, same
      environment hash → reused. Same name, different hash → the running container is DELETED
      and then recreated** (`instances.ts:165–168`). A new release is a new name, and **the old
      container is left running**;
   3. **`applyRoute`** (`driver.ts:349` → `routing/routes.ts:21`): **`DELETE /id/<route>` then
      `PUT …/routes/0`**, dialling `<container>:<port>`. **The public route moves to the new
      container before it answers**;
   4. **`waitForReady` + `edgeProbe`** (`driver.ts:372`, `routing/readiness.ts:75`): a
      throwaway `curl` container on `manifest-platform` requests
      `https://<public hostname><health path>` through the edge and accepts **status 200 — the
      status only**. On failure it throws `InstanceNotReadyError` with the handle.
3. **`waitForHealth`** (`release.ts:496`) reads the container's own HEALTHCHECK.
4. The instance row becomes `healthy` or `failed`; events are published; on healthy,
   **`commitAppKey`** (`release.ts:639`) stores the new key and **revokes the previous one**.
5. **Nothing retires the old instance.** `destroyInstance` (`driver.ts:400`) would remove the
   route **by hostname** (`driver.ts:418`), which the new instance shares (P4b finding 75).
6. **On a failed deploy, the route is not moved back.** The route moved at step 2.3; nothing
   restores it, so a failed redeploy leaves the public hostname on the failed container and the
   app down until a good deploy. *Read from the code, not measured.*
7. **The contract suite says nothing about continuity.** `runtime/driver-contract.ts` has
   13 tests; none observes a route, an overlap or a drain. The fake driver
   (`runtime/fake-driver.ts`) has no route at all, and P4b finding 73 is the precedent: the
   two drivers disagreed about container reuse and no contract test could see it.

## 3. Measured on 2026-09-15

macOS 26.6.2, Docker Engine 29.7.2, the custom Caddy 2.11.4 edge, the proof app on
`node-ts-mongo@1` (`node:22-alpine`, `express-session` 1.19.0), LiteLLM 1.98.0.

### 3.1 A redeploy under load — the baseline the roadmap asked for

A `/healthz` loop every 200 ms (under the route's 600/min rate limit), **classified by body**,
and a signed-in student asking questions back to back. Times are from the deploy call's start.

| | Same-release redeploy | New-release redeploy |
|---|---|---|
| Deploy call | 5,723 ms | 5,473 ms |
| `/healthz` (deploy start to end + 5 s) | 54 requests: 47 app, **7 × 502 with an empty body**, from +428 to +1,634 ms | 52 requests: 46 app, **6 × 502 empty**, from +411 to +1,417 ms |
| The student's questions | the one in flight finished 200 at +218 ms; then **16 × 502** to +1,659 ms; then **401 — signed out**; signed in again → 200 | the one in flight finished 200 at +519 ms; then **12 × 502** to +1,610 ms; then **401 — signed out**; signed in again → 200 |
| The old container | deleted before its replacement answered | left running, unrouted |

What that means:

- **Every redeploy is a window of empty 502s about as long as the app takes to boot.** The
  proof app boots in about a second; a slower app's window is longer. There is no platform
  number to quote.
- **EVERY REDEPLOY SIGNS EVERY USER OUT.** The first request to the new container answered 401,
  on both kinds of redeploy. The blueprint's skeleton uses `express-session` with no `store`,
  so sessions live in the container's memory (`MemoryStore`, which its own authors say is not
  for production). The platform keeps `SESSION_SECRET` stable across deploys *so that sessions
  survive*; the in-memory store defeats that. §3.3 shows it directly.
- **A same-release redeploy destroys the live container before its replacement exists** — and
  every AI app takes this path on every same-release redeploy, because a new key is minted each
  time and changes the environment hash.
- **A new-release redeploy already creates an overlap** — the old container keeps running — but
  nothing uses it, drains it or retires it.

### 3.2 The edge: three ways to move a route

A throwaway route on `p4c-probe.staging.manifest.internal`, moved between two running proof-app
containers 20 times per mechanism, with a request every 25 ms.

| Mechanism | Requests | App | **Wildcard `200`** | Connection reset |
|---|---|---|---|---|
| **delete-then-insert** — today's `applyRoute` | 320 | 309 | **4** | 7 |
| **`PATCH /id/<route>`** — the whole route replaced in place | 302 | 300 | **0** | 2 |
| **`PATCH /id/<route>/handle/3/upstreams/0/dial`** — the dial only | 301 | 298 | **0** | 3 |
| *Control:* 7 s, no config change, keep-alive client | 312 | 312 | 0 | 0 |
| *Control:* 7 s, no config change, new connection per request | 311 | 311 | 0 | 0 |
| `PATCH` the dial, 20 moves, keep-alive client (second run) | 299 | 298 | 0 | 1 |
| `PATCH` the dial, 20 moves, new connection per request | 298 | 297 | 0 | 1 (`ECONNRESET`) |

What that means:

- **Delete-then-insert has a gap, and the edge's wildcard fills it with a `200`** —
  `manifest OK host=…`. A check that reads the status sees nothing wrong (P4b finding 193).
- **An in-place `PATCH` has no gap.** Every admin call answered 200.
- **Every admin API change reloads Caddy's configuration, and a reload occasionally resets a
  connection** — about one request in 300 across 20 changes, for new connections as well as
  kept-alive ones, and never with no change. The route being changed is not special: **any
  app's deploy can reset a request to any app.** Browsers retry an idempotent request on a
  reset connection; a `POST` is not retried. "Zero failed requests" through admin-API changes is
  therefore not a guarantee this edge can make as configured — see §6, decision 1.

### 3.3 A request in flight when the route moves

A signed-in student's question (3–4 s long) started on the throwaway route; one second in, the
route moved to the other container.

| Trial | The question in flight | A NEW request afterwards, same session cookie |
|---|---|---|
| no move (control) | 200, 3.0 s | — |
| `PATCH` dial × 3 | **200** every time, 3.3 / 4.2 / 4.3 s | **401** every time |
| delete-then-insert | **200**, 4.1 s | **401** |

**Caddy lets a proxied request finish on the upstream it started on**, whichever way the route
moves. So a drain is *keep the old container running until its in-flight requests end* — the move
itself does not cut them off. And the 401 is the session store of §3.1, seen directly: the session
exists only in the container that created it.

### 3.4 Facts from earlier sittings that bind P4c

Each is in ORIENTATION §4 or P4b's record; they are here because a redeploy design meets all of them.

- **LiteLLM checks a key when a request STARTS** — a stream whose key was revoked mid-way ran to a
  normal finish. So revoking the old key is safe for requests already in flight and fatal for any
  that start after it.
- **An app whose gateway vanishes under a pooled connection waits 611 s** (P4b finding 181). A step
  that detaches or recreates `manifest-litellm` must not happen while an app is serving.
- **A host process cannot reach container IPs** on Docker Desktop. A probe goes through the edge or
  runs from a container — `edgeProbe` already runs one on `manifest-platform`.
- **`edgeProbe` reads the status only, and the wildcard answers 200 for a hostname with no route**
  (193). A readiness probe aimed at a hostname that is not routed yet **passes**.
- **Restarting Caddy drops every runtime route**, and the control plane re-applies them only at its
  own boot (`reapplyAllRoutes`). `pnpm test:docker` restarts the edge.
- **Caddy admin: `PUT` at `routes/0` inserts; `POST` appends behind the wildcard**, which is
  `terminal`, so an appended route is never reached.
- **Each instance has a NAMED `-files` volume holding its copy of the SP private key**; `docker rm -v`
  leaves it (194). Retiring an instance must remove it.
- **`docker ps --filter name=A --filter name=B` is an OR** (192) — anything that selects containers
  to retire by filter must narrow explicitly.
- **A network removed under a stopped container strands it** (P4b finding 77).
- **The event WebSocket is served by the control plane on 7100 directly, not through the edge.** An
  app's route move cannot touch it; a control-plane restart would, and that is not P4c's. *(The
  roadmap row's item 4 named it as at risk from a route change; it is not.)*
- **Hibernation uses the same path**: `stopInstance`, then `ensureInstance` wakes the container by
  name (§11). A redesign of `ensureInstance` must keep the wake path working.

## 4. The roadmap's five questions, with what is now known

1. **A baseline first.** Done — §3.1. The plan should re-measure it in its first task, as a Docker-
   tier or demo check, so the final acceptance compares against a number it produced itself.
2. **Where the guarantee lives.** In the §11 contract, so the fake driver and the contract suite
   carry it. The suite must be able to **observe the route** — which instance the public hostname
   reaches — or it cannot see the defect it exists to prevent (§2.7).
3. **Two releases sharing one database during the overlap.** Unavoidable once old and new serve at
   once, and it now includes **sessions**: if users are to stay signed in (§6, decision 2), the
   blueprint needs a session store both containers share — a Mongo store is the natural one — which
   is a new pinned dependency, through the scan gate, with Verdaccio re-warmed (network on). Schema
   changes between releases are a rule for the knowledge pack (expand, migrate, contract); nothing in
   Phase 1 can enforce one.
4. **In-flight requests and long streams across a route change.** Measured — they finish on the old
   upstream (§3.3). What remains is how long the old container waits (§6, decision 3), and that
   an AI answer can take tens of seconds.
5. **Retiring old instances.** A straight-line step after the drain — the container, its `-files`
   volume, and its key — that **does not remove a route the new instance owns**. It also closes
   RUNBOOK's leaked-container gap for every redeploy from P4c on; the backlog of containers from
   before is decision 6.

## 5. One shape the measurements support — an option, not a decision

Offered as a starting point for brainstorming, so the design conversation starts from something
coherent. Every step is grounded in §3; none is decided.

1. **Start the new instance alongside the old one**, under a name unique to the deploy, so no deploy
   ever deletes the container that is serving. *(Today a same-release redeploy does exactly that.)*
2. **Make it ready privately**, without touching the public route — for example, probe
   `http://<container>:<port><health>` from a container attached to the app network, or through a
   non-public per-instance route. Whatever the probe, it must **prove it reached THIS instance** —
   a body or a response header naming the instance — never a status (§3.4).
3. **Move the route with one in-place `PATCH`** — no gap (§3.2).
4. **Verify through the edge that the public hostname now reaches the new instance, by identity.**
   A `headers` handler in the route that sets, say, `X-Manifest-Instance` makes this provable and
   gives every later check something to assert.
5. **Commit the new AI key.**
6. **Drain**: keep the old instance running until its in-flight requests have ended — bounded by a
   drain timeout (§3.3).
7. **Only then** revoke the old key (§3.4: LiteLLM checks at request start), and destroy the old
   container and its `-files` volume — without touching the route.
8. **If the new instance never becomes ready**: the route never moved, the old instance keeps
   serving, the new container and its key are discarded, and the Incident is recorded as today.
   *(Today a failed redeploy takes the app down — §2.6.)*

**Two interface shapes for §11**, each with a cost:

- **`ensureInstance` keeps its signature and changes its meaning** (start, ready privately, move),
  plus a new `retireInstance(previous, { drainMs })`. Fewer call-site changes; the move stays inside
  one method, where the contract suite can only see it through the route.
- **Explicit steps** — `startInstance`, `promoteInstance`, `retireInstance`. The guarantee is visible
  in §11 and each step is testable on its own; `deployRelease` orchestrates, and a Phase 5 driver has
  to implement three things rather than one.

**Not measured, and worth a look before choosing:** Caddy's own load-balancing options — several
upstreams in one route with health checks and retries on a failed dial — might move traffic with
fewer config reloads, and so fewer resets (§3.2). Untested here.

**Out of scope, deliberately:** the reconciler (Phase 4, D10), crash-loop detection, multiple hosts,
production database blue/green, and a control-plane restart that keeps its WebSockets.

## 6. Decisions that are Rich's — put them to him early

1. **What "not interrupted" means.** Zero 5xx and zero wildcard responses, with the rare connection
   reset a Caddy config reload causes tolerated (§3.2)? Or zero failed requests of any kind — which
   would mean changing how the edge is reconfigured, not only when.
2. **Do users stay signed in across a redeploy?** Today every redeploy signs everyone out (§3.1).
   Keeping them signed in is a blueprint change: a shared session store, a new pinned dependency.
3. **How long an old instance drains.** An AI answer runs for seconds to tens of seconds.
4. **A failed new release keeps the old one serving** — the recommendation — which changes what a
   failed deploy means in §11 and §13 (today: the app is down).
5. **The §11 wording.** Already his (roadmap P4c row).
6. **The backlog.** Does P4c reap containers left by redeploys before it, or only retire the one
   each redeploy replaces?
7. **Schema changes between releases that share a database.** A knowledge-pack rule only, or
   anything the platform checks?

## 7. A suggested acceptance, for the plan to adopt or change

**`make demo-redeploy`** — or a step of `make demo-ai` — with the proof app serving:

- run a request loop **classified by body** and a signed-in student asking questions back to back;
- redeploy the **same release**, then a **new release**;
- assert: **no** 502, **no** wildcard body, every question answered 200 — and **no 401** if decision 2
  keeps users signed in; exactly one app container at the end, the old one's `-files` volume gone, and
  the old key revoked only after the drain;
- and a **failed release**: the old instance keeps serving, the route never moves, an Incident is
  recorded.

**Negative controls it should come with**, each watched red: restore delete-then-insert (wildcard
bodies appear); move the route before readiness (502s); revoke the old key at commit rather than after
the drain (an AI call that starts during the drain fails); skip the drain (an in-flight question
fails when the old container is destroyed); make the readiness probe status-only against an unrouted
name (it passes on the wildcard).

## 8. Lessons from P4a and P4b that will bite this plan

- **Schedule the end-to-end redeploy check in the first tasks, not the last.** Every worst defect in
  this project arrived the first time something ran end to end.
- **Assert identity or body, never a status** — the edge's wildcard answers 200 (193), and a status-
  only readiness probe cannot tell the app from the placeholder.
- **Make the two drivers agree, and make the contract suite able to see the route** (finding 73).
- **Name each step's caller.** A `retireInstance` nothing calls is not built.
- **Cleanup has traps**: `name` filters OR (192), and each instance's files volume is named and holds a
  private key (194).
- **A redeploy mints an AI key**, so every redeploy test also exercises key commit and revoke — test the
  drain against a real AI call, not a health check.
- **Every sitting ends with the four gates, the Docker tier, a record and ORIENTATION §6's sweep.**
