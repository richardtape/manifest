## Critical

**C1. Requests are never validated, and the record-answer form leaves out the fields the operation requires.**

- **The contract.** `RecordIamRegistrationRequest.required` is `entityId`, `acsUrl`, `sloUrl`, `registeredAttributes` and `state`
  (`openapi.json`).
  - `environment` is *"production's when absent"* (`launch/records.ts:170`).
  - `registeredAttributes`: *"Once registered, a record that does not reach `active` must repeat them unchanged."*
  - `requestedAttributes` is required for `active → change_requested` (`records.ts:224-232`).
- **The platform writes what it is sent.** It upserts `entityId`, `acsUrl`, `sloUrl` and `registeredAttributes` from the body
  (`records.ts:291-294`, `:314-317`).
- **The plan.** Task 2's `recordIamRegistration(projectId, body, idempotency)` (plan l.658) and Task 8's pane name only the state
  control (*"the answer form offering exactly `IAM_MOVES[state]`"*, l.1324). Task 4's rules for the fleet's record route name only the
  transition (l.822-824).
- **The mock cannot catch it.** It validates answers, never requests (`server.ts:1539-1556`; the plan says so itself, l.812).
  - Its record routes answer the fixture whatever is sent (`server.ts:656-660`).
  - So a console that sends `{ state: 'active' }` passes every planned test and the walk.
- **What goes wrong on the platform:**
  - Every recorded answer is `400 REQUEST_INVALID`.
  - If the pane fills the fields from the wrong source, it overwrites what UBC registered.
  - A staging item recorded without `environment` is written to production's registration.
  - That is the gate's integrity (§13), which is the record's whole purpose.
  - This is the false green P3 paid for: the test builds the value right, and the running system reads it differently.
- **Fix:**
  1. **The fleet validates the REQUEST body of every mutation it acts on** against the operation's request schema. The validator takes
     any component name (`validate(schema, value)`, `validate.ts`). On failure it answers `400 REQUEST_INVALID` naming the field, as
     the platform does. Give `fleet.test.ts` one case per operation, with a required field missing, each asserting the code.
  2. **Task 8's form for UBC's answer always sends:**
     - `environment`, from the queue item's `environment`;
     - the record's own `entityId`, `acsUrl`, `sloUrl`, `certFingerprint`, `certExpiresAt` and `externalTicketRef`;
     - `registeredAttributes` — for `active`, what UBC registered, pre-filled from the requested or package attributes and editable;
       for every other move, the record's own, unchanged;
     - `requestedAttributes` where a change needs them.
  3. `record-pane.test.tsx` asserts the exact body for each move. The walk's check 6 reads the record back and asserts that its
     `entityId` and attributes are unchanged and that staging, not production, moved.
  4. Do the same for `RecordSubmissionRequest` (`sentAt` is a `date`) and `RejectPendingActionRequest` (`reason` required). Task 4's
     *"`fleet.ts` refuses it itself"* (l.812) becomes *"the request schema refuses it"*.

**I7. The mock refuses the retry of any request that carries a reason. Review Focus 1 fails on the one action that sends one.**

- **The defect.** The replay check hashes the body **plus** `\0<reason>` when a `Manifest-Admin-Reason` is sent
  (`server.ts:1460-1463`). The store keeps `JSON.stringify(body ?? null)` **without** it (`:1559-1561`).
  - So a retry with the same key and the same reason is `409 IDEMPOTENCY_KEY_REUSED`, never the replay.
  - It is pre-existing (the faculty-ready plan's Task 10).
- **Why it matters here.** The demo fleet makes a reason-carrying write ordinary: Task 10's reject sends the header, because Operator
  One is no member. The plan's Global Constraint is one key per action, reused on a retry (l.396).
- **Fix:** Task 4 stores the hash as computed at `:1461`, red first, with a `server.test.ts` case:
  - with a reason, a retry with the same key and reason → the replay;
  - with another reason → `409`.
  - Name it in L1's G3 notice: a default answer changes, towards the platform's. Pin Review Focus 1 in Task 10 as in Tasks 7 and 8.

**I8. (P11P's, after `b5fd9fe`; confirmed.) A granted change request is two writes, and the platform has no arrow from
`change_requested` to `active`.**

- **The arrows.** `IAM_ARROWS.change_requested` is `['submitted', 'expired']` (`launch/transitions.ts:47`).
- **The plan and design.** The design's §3.5 and the old mockup offer `active` from an `iam-change-request`. The platform refuses it
  with `409 LAUNCH_TRANSITION_INVALID`.
- **Confirmed, and two consequences added:**
  - The first write (`change_requested → submitted`) stamps a **new** `submittedAt` (`records.ts:263-269`). The item flips from
    `iam-change-request` to `iam-registration`, its `since` reset to now (`queue.ts:290`). If the second write fails, the 21 days UBC
    held it vanish from the queue, and the item reads as freshly submitted.
  - Two writes are two Idempotency-Keys. The pane must treat them as one decision: run them in order, retry the second on its own key,
    and, if the second never lands, show the record at `submitted` and offer *"record UBC's answer"* again.
  - The in-force registration is not interrupted. `registeredAt` is kept through `change_requested → submitted` (`records.ts:249-253`),
    so `readiness.ts:552`'s in-force check still reads `met`, and production deploys continue between the writes.
- **Fix (as P11P proposes, with the above):** file design finding A20. Task 8's pane offers the platform's moves and says, beside them,
  that a granted change is recorded `submitted` then `active`. Add a test for the two-write sequence and for a failed second write.
