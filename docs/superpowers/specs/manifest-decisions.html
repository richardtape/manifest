The 32 decisions

Every significant choice made while designing Manifest, with the reason it was made. Most of them are here because the obvious alternative turned out to be wrong, and it is worth remembering why.

Filter by theme or search the text Full detail §4 of the design document

A decision is written down when reversing it later would be expensive. Small choices are not here. These 32 are.

D1

A sandbox, a test copy and a live app are all the same kind of thing to Manifest — one object with three different lifespans.

If they were three separate systems they would drift apart, and the version a faculty member tested would stop resembling the version students use. Building it once means what you tested is what ships.

Running apps
D2

The AI that writes the app runs inside the sandbox, and gets its access to language models handed to it in a form that expires.

The real account keys for the model providers are never anywhere the AI can read them. If the AI is tricked into leaking what it holds, what leaks is a short-lived, spend-capped key for one project.

AI
D3

Every app gets its own private database rather than sharing one.

Two benefits. One app can never read another’s data, and when an app goes to sleep its database sleeps with it — so a course tool nobody has opened since April costs nothing to keep. The cost is more databases to back up, which is the platform team’s problem rather than a faculty member’s.

Running apps
D4

Each app carries a short settings file describing what it needs — a database, sign-in, an AI model — and that file lives with the app’s code.

It travels with the app, so its history is visible: you can see exactly what changed and when. It is also the thing a reviewer reads before approving a launch, instead of reading thousands of lines of code.

Choices & tools
D5

Where an app’s code is stored is swappable. Version one keeps it on the machine Manifest runs on; version two can keep it in a UBC GitHub account.

It means the whole platform can be run and demonstrated on one laptop with no accounts, no tokens and no internet connection. Moving to GitHub later is a setting, not a rebuild.

Choices & tools
D6

There are two separate sign-in systems. Practice apps use a Manifest-run copy with fake test users. Live apps use the real UBC CWL, registered one app at a time.

UBC requires a separate registration for every live application, decided by people rather than by software — so it cannot sit inside a daily build loop. A side benefit: the practice sign-in system never touches a real person’s identity, so breaking into it gets you nothing.

Signing in
D7

Manifest uses an existing tool to manage AI model access rather than building its own.

That tool already handles spending caps, per-project keys and switching between model providers. Writing a second one would be work with no payoff.

AI
D8

AI spending is tracked per app, per build session, and per person using the app.

An AI stuck in a loop spends only its own allowance and then stops. And when a course tool’s AI budget runs out in week three, you can answer “which of the 300 students spent it” rather than guessing.

AI
D9

A human approves an app once, before it first goes live. After that, updates ship freely — unless the app starts asking for something new and sensitive, which sends it back for approval automatically.

Reviewing every update would make the platform useless. Reviewing none of them would let an AI quietly add a new database, a new outside connection or a request for more personal information about students. This catches exactly those changes and ignores the rest.

Safety
D10

The first version does things in a simple straight line. The self-correcting version that constantly checks and repairs the fleet comes later, wrapped around it.

Building the clever version first means guessing what the problems are. Building the simple version first means finding out. The later work adds to this rather than replacing it.

Running apps
D11

Manifest itself is built in TypeScript with a Postgres database.

It is what the team knows, and the AI-access tool Manifest depends on already needs a Postgres database — so this adds nothing new to run.

Choices & tools
D12

Traffic arrives through one piece of software with two entirely separate front doors: one reachable only from inside UBC, one open to the public. Practice apps are only ever wired to the first.

The alternative is one door with a list of who is allowed through. Lists get edited wrongly and fail silently — the app stays reachable and nobody notices. A wrong door simply does not open.

Running apps
D13

Apps cannot supply their own build instructions. Those come from the blueprint.

The moment an app is built is the moment the platform is most exposed, because building means running whatever instructions it was given. Letting an app supply those is handing it the keys. It also breaks the rule that an app says what it needs, never how to provide it.

Safety
D14

The genuinely consequential actions — going live, reading a password, raising a spending limit, adding someone to a project — always need a person, signed in, clicking. No AI can do them, ever, no matter whose AI it is.

An AI can be talked into things by text it reads: a student’s uploaded PDF, a web page, a note buried in a software package. That makes any AI a potential stand-in for an attacker. Written this way, the rule protects equally against an AI running here and someone’s own AI on their own laptop. It is the single most important rule in the design.

Safety
D15

Manifest works out the web address that sign-in results get sent back to. An app can suggest a path within itself, never a full address.

Registering an app for CWL means telling UBC where to deliver proof of who just signed in. If an app could name any address, a mistake or a manipulated AI could have that proof delivered somewhere else entirely.

Signing in
D16

Asking for a new piece of personal information about users needs approval everywhere, not just in the live app.

A live app may only receive what UBC agreed to release when it was registered. Catching a new request during practice turns a login that would have failed on launch day into a question raised while there is still time to answer it.

Signing in
D17

How sensitive an app’s data is decides which AI models it is allowed to use.

A BC public body sending student personal information to a model running in the United States is a privacy problem. Both facts were already recorded separately; connecting them was nearly free and closes a gap that was one careless line away from opening.

Safety
D18

No app can reach anything on the internet unless it has said in advance what it needs to reach. This applies to live apps, not just practice ones.

An earlier draft only restricted practice apps, on the reasoning that they run unreviewed code. But a live app runs for years, holds real data and sits inside UBC’s network — if something goes wrong there it is a far better foothold than a sandbox that disappears in 45 minutes.

Safety
D19

Manifest writes the first draft of the two documents every live app needs — the sign-in registration and the privacy assessment — and tracks them until they are approved.

The platform knows more about the app than its owner does. It can work out what personal information the app will handle and why, so a faculty member reviews and signs rather than starting from a blank form, and what reaches a reviewer is complete the first time. Both are deliberately modelled as tracked objects with a status rather than as attachments to an email, so that submitting by hand today and handing them over electronically later are the same step with a different mechanism behind it.

Signing in
D20

The security certificate that proves an app’s identity to UBC is issued once and kept for years. Its expiry date is watched and warned about months in advance.

That certificate is registered with UBC, so replacing it routinely would break sign-in every time. The opposite failure is worse: an expiry nobody noticed silently kills login for a live course tool in the middle of term, and looks like a mystery until someone checks a date.

Signing in
D21

Before an app goes live it does one rehearsal sign-in against UBC’s real test system.

Practising against Manifest’s own sign-in keeps daily work fast, but an app whose first contact with the real system is launch day will fail on launch day. The rehearsal is the only way to find that out while it is still fixable.

Signing in
D22

This project builds its own basic web console early, deliberately restricted so that it can only use what the public interface offers.

Two payoffs. The faculty journey becomes something you can click through and show people in month two rather than month eight. And if the console ever needs something the public interface cannot do, the build fails — so “is the interface complete?” stops being an opinion and becomes a test.

Ways in
D23

The public interface describes things, not screens, and it is deliberately tied to no particular AI toolkit.

If the interface were shaped around today’s screens, the real front-end team could never lay things out differently without asking us to change the back-end first. And AI toolkits change fast — an earlier prototype had to pin itself to one exact version and recorded that as a standing risk. That risk must not reach this interface.

Ways in
D24

There are two kinds of access. A person signed in through a browser can do anything they are entitled to. A token held by an AI or a script can do a great deal but never the four consequential things — those queue up for a person to confirm.

This is what makes “bring your own AI” safe rather than a loophole. Worth noting how much a token still covers: creating projects, reading everything, building, testing, watching logs — the entire day-to-day loop. Only four actions need a human.

Safety
D25

The instructions that teach an AI how to build for this platform are published through the interface, not only placed inside the sandbox.

Somebody using their own AI on their own laptop cannot read a file inside a sandbox they never run. Without publishing them, that person’s AI has no way to learn the platform’s conventions — which is precisely the knowledge that makes the difference between an app that works here and one that does not.

Ways in
D26

Every app has a permanent Manifest web address that never changes. A department’s own address is added alongside it, never instead of it.

Sign-in registration, health checks and internal tooling are all pinned to that permanent address, and none of them should depend on what someone typed into a domain field last week. It also decides what happens when things go wrong: if the department’s address lapses or its DNS is restructured, the app degrades to working on an ugly address rather than going dark.

Addresses & size
D27

If an app uses CWL sign-in, its custom web address must be chosen before its UBC registration is submitted. Changing it afterwards means going back through that registration.

The address is written into the registration, because it is where UBC delivers proof of who just signed in. This is the single mistake faculty are most likely to make: choosing an address is a five-second decision in week one, and changing it costs a month in week twelve. So Manifest asks the question at registration time rather than offering it later as a convenience. Apps with no sign-in can change address whenever they like.

Addresses & size
D28

A custom address has to be proven before it can be used, by way of two DNS records the department creates. The security certificate is then issued automatically.

Without proof, one project could claim an address belonging to another. The first record points traffic here; the second proves this project was the one authorised to claim it. Requiring the first also means the certificate can be issued immediately — traffic already arrives, so there is nothing left to check. Departments that cannot create those records upload a certificate instead, and Manifest watches its expiry just as closely.

Addresses & size
D29

How many people an app is for, and whether they all arrive at once, are answered by a person when the project is created — not written in the app’s settings file.

A faculty member can answer “who is this for” and cannot answer “how many servers”. Keeping it out of the settings file matters for a second reason: that file is written by AI, and capacity costs real money, so a field an AI can edit is a field an AI can be talked into multiplying twentyfold. The two questions are separate because 200 students over a week and 200 students at 10:03 on Tuesday are different problems with the same headcount.

Addresses & size
D30

Each blueprint carries a description of itself — its language, what it can connect to, what it needs. Manifest reads that description and assumes nothing about any particular language. Only one blueprint ships at first.

This is the difference between the second blueprint being a new folder and being a rewrite. Without it, assumptions about the one language quietly settle into the build process, the health checks and the list of available databases, and every one of them surfaces the week somebody asks for Python. Describing one blueprint is cheap; untangling four unwritten assumptions later is not.

Choices & tools
D31

The admin dashboard uses the same public interface as everything else, with administrator rights — not a private back door. Its main screen is the list of things waiting on a person.

A private admin interface would drift out of step, and would become the place where useful capabilities land that faculty then cannot have. The choice of main screen matters more than it sounds: the design deliberately routes a specific set of actions through human judgement, so how many people are waiting on an administrator is the platform’s central health measure, not a footnote.

Ways in
D32

Starting from someone else’s app gives you their design and their code, and none of their trust. No data, no passwords, no sign-in registration, no privacy approval, no web address, no size setting.

Forking is the platform’s best answer to forty people building the same marking tool, so it has to be safe enough to encourage. Everything on the not-copied list belongs to one person, one group of students and one purpose: copying a sign-in registration would put two different applications behind one identity at UBC, and copying a size setting would quietly size a fourteen-person tool for nine hundred. What you do inherit is the expensive part — the design, the code, and a privacy draft a reviewer has already accepted for a very similar app.
