What gets built when

Manifest is built in eight stages. Each one ends in something you can open in a browser and show to somebody — not a status report, an actual working thing.

Now stage 1a, the first plan Full detail §17 of the design document

01 — Questions first

Seven experiments, before any of it

Before the real build starts, seven small throwaway experiments answer questions that would be ruinously expensive to get wrong later. Each one takes days, not weeks. Every one of them is meant to be deleted afterwards.

ExperimentThe question it answersWhy it cannot wait
S7 · first Does the whole platform actually run on one laptop, with the internet switched off, from a fresh copy? The entire first stage is built on the assumption that it does. If it does not, we need to know in week one.
S2 · first Can we register an app for sign-in by adding a row to a database, rather than editing files by hand? If not, the whole approach to practice sign-ins has to be redesigned — better learned in an afternoon than in month two.
S1 Can we go from source code to a running, reachable app with a working database? It is the single most basic thing the platform does.
S3 Do AI model access, spending caps and a locally-run model work together on a Mac? Everything about offline AI depends on the answer.
S6 If somebody hostile got inside a sandbox, what could they actually reach? Required before the platform first runs code nobody has reviewed. Its output becomes a permanent set of security tests.
S4 Can a sleeping app be woken by someone visiting it, without them seeing an error? Needed for apps to cost nothing while idle. Can run alongside other work.
S5 Can an AI work inside a sandbox and produce a real code change? The heart of the product, but not needed until stage 3.

The first two run before anything else. S6 must finish before stage 3, when the platform first executes code that nobody has read.

02 — The eight stages

Each one ends in something you can show

Stage 1 is deliberately split into three. Written as one stage it was a platform rather than an increment — fifteen separate pieces at once, with no honest way to sequence them.

1afoundations

The ground it all stands on

Everything needed to take source code, turn it into a running app, give it a database and put it at a working web address — on one laptop, offline, from a fresh copy. All the security containment lands here too: apps isolated from each other, unable to reach the internet unless they have said what they need, unable to reach the platform that runs them.

You can show: a small test app, running and healthy at a real web address, from a clean checkout, with the network switched off.

Does the “runs on a laptop” promise hold, and is the isolation real?

1bthe real loop

Sign-in, secrets and AI

Apps can register themselves for practice sign-in, hold passwords safely, and call an AI model within a spending cap. The first blueprint arrives, along with the description of itself that lets later blueprints be added without a rewrite.

You can show: a real app where you sign in, save something to your own database and ask an AI a question.

Is the loop genuinely real, end to end?

1cways in

The public interface and a console to prove it

The published interface everybody builds against, a basic web console that uses nothing but that interface, and tokens so somebody’s own AI can drive the same thing from their own laptop. The question “who is this app for?” starts being asked here, even though nothing acts on the answer until stage 2.

You can show: the whole faculty journey, clickable, driven twice — once by a person and once by a script — over the same interface.

Is the interface complete, and can a second developer reproduce all of it?

2going live

Live apps, approvals, addresses and size

Real production apps, promoted from the tested version without rebuilding. The launch checklist becomes a gate that actually blocks. Custom web addresses, proven by DNS and given certificates. The size question starts having an effect on capacity. The admin dashboard arrives, built around its queue.

You can show: an app legitimately launched, with its paperwork approved and its department’s own address on it.

Is it safe, and can we get an app genuinely launched?

3the AI part

Sandboxes and building by describing

An AI can now work inside a sandbox: writing files, running commands, showing a live preview. A chat panel is added to the same console. Manifest also becomes available as a set of tools any AI can use directly, which is what makes “bring your own AI” real rather than theoretical.

You can show: describing an app in a sentence and watching it appear. The separate faculty-facing front-end project can begin here, against an interface that has already been exercised.

Can an AI actually build in this environment?

4scaling down

Self-correction and sleeping apps

The straight-line process becomes a loop that continually checks what should be running against what is, and repairs the difference. Idle apps sleep and wake when somebody visits.

Does it cost nothing when nobody is using it?

5leaving the laptop

Real UBC infrastructure

A second way of running apps — on UBC servers or a cluster, whichever UBC chooses — that passes the identical set of tests the laptop version passes.

Does it work anywhere other than a developer’s machine?

03 — Why this order

Four sequencing choices worth defending

Security is in stage 1a, not spread through the middle

Manifest’s core job is to safely contain code that nobody has reviewed. That has to be true before anything runs, not added once apps and databases already exist. Retrofitting isolation is exactly the kind of rework the rest of the plan avoids.

The blueprint’s self-description cannot wait

It is the one piece of the recent additions that has to land early. Everything else adds capability to a platform that already works. This one, added late, means untangling assumptions about a single language that will by then be woven through the build process, the health checks and the list of available databases. Doing it now costs a day; doing it in stage 5 costs a rewrite.

The UBC paperwork starts during stage 1

Registering an app for CWL and getting a privacy assessment approved both take weeks, and both happen outside the team. Starting them after stage 2 would leave a finished platform sitting idle waiting on tickets. Starting them in parallel means stage 2 ends with an application that can genuinely launch — and it tests the paperwork Manifest generates against a real reviewer while it is still cheap to change.

The console comes before the real front-end

The faculty-facing front-end is a separate project. If its team discovered gaps in the interface in month eight, those gaps would be expensive and they would be blocked. Building a plain console here in stage 1c finds the same gaps in month two, when fixing them is a morning’s work.

04 — What waits

Things deliberately not built yet

Each of these has a place to slot into later. None of them requires going back and undoing something.

  • More than one blueprint. One ships first. The catalogue, the version pinning and the self-description all exist from stage 1, so a second is a new folder.
  • Canvas and other UBC system connections. There is a reserved, currently-empty place in every app’s settings file for them.
  • Scheduled background jobs — nightly reminders, weekly digests. Same: reserved and empty.
  • Apps that bring their own build instructions. Deliberately refused for now, because building is the moment the platform is most exposed. It may return later behind stronger isolation.
  • A general-purpose hosting platform. Manifest serves AI-built UBC teaching and research apps. That focus is what lets it make promises a general platform could not.
